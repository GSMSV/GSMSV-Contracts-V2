# 21번(인스턴스를 팀 단위로 소유) — 팀과 역할

> 읽는 사람: GSMSV v2를 개발하는 사람(Kotlin API, Go 인프라 연동, React). 이 문서만 읽고 구현할 수 있게 이유와 하면 안 되는 것까지 적었다.
>
> 함께 읽을 문서: [22번(권한 판단 Layer)](authorization.md) · [23번(자원 이름 규칙)](resource-naming.md)
>
> 표기: 따로 표시가 없으면 **확정**이다. 아직 정하지 않은 것은 **미정**, 논의 중에 나온 안은 **제안**이라고 적었다.

## 1. 무엇을 하는 기능인가

팀을 만들고 사람을 초대해서, 팀이 소유한 VM을 팀원 모두가 역할에 따라 함께 관리한다.

- 같은 프로젝트를 하는 학생들이 한 VM을 함께 보고 관리할 수 있어야 한다. 한 사람만 VM을 소유하면 다른 팀원은 그 VM을 볼 수도, 관리할 수도 없다
- 그래서 프로젝트 오너라는 별도 계정 종류를 없애고, 사용자끼리 만드는 **팀**으로 대신한다
- "누가 자원을 소유하는가"는 모든 테이블, 모든 API, 모든 권한 검사에 들어간다. 나중에 바꾸면 전면 수정이 되므로 개발 시작 전에 정했다

## 2. 누가 무엇을 할 수 있는가

### 2.1 역할

- **전역 역할은 둘뿐이다**: 일반 사용자(USER)와 관리자(ADMIN). 프로젝트 오너(PROJECT_OWNER)는 두지 않는다
- **팀 안의 역할은 셋이다**: 팀장, DevOps 엔지니어, 일반 팀원
  - 같은 사람이 팀마다 다른 역할을 가질 수 있다. 예: 팀 A에서는 팀장, 팀 B에서는 일반 팀원
  - 그래서 권한은 전역 역할만으로 판단할 수 없다. 자원이 어느 팀 것이고 그 팀에서 요청자의 역할이 무엇인지를 매번 본다 ([22번](authorization.md))
- **시스템(자동)**: 팀장이 나갔을 때 새 팀장 정하기, 팀 VM 만료 처리, 알림 보내기를 한다

### 2.2 역할별로 할 수 있는 일 (팀 VM과 팀)

| 동작 | 일반 팀원 | DevOps 엔지니어 | 팀장 | 관리자 |
|---|---|---|---|---|
| 팀 VM 목록·상태 보기 | ✓ | ✓ | ✓ | ✓ |
| SSH 접속 명령어와 비밀번호 보기 | ✓ | ✓ | ✓ | ✓ |
| 사용 기간 연장 신청 | ✓ | ✓ | ✓ | ✓ |
| 팀 VM 관련 알림 받기 | ✓ | ✓ | ✓ | |
| 팀 탈퇴 | ✓ | ✓ | ✓ | |
| 팀 VM 생성·삭제 | | ✓ | ✓ | ✓ |
| 전원 제어(켜기·끄기·재시작) | | ✓ | ✓ | ✓ |
| 사양 변경, 스냅샷, 포트포워딩, 방화벽, HTTPS 도메인 연결 | | ✓ | ✓ | ✓ |
| DevOps 역할 회수 | | 본인만 | ✓ | ✓ |
| 팀원 초대·제외 | | | ✓ | ✓ |
| DevOps 역할 부여 | | | ✓ | ✓ |
| 팀 해체 요청 | | | ✓ | ✓ |
| 팀장 넘기기 | | | ✓ | ✓ |
| 팀 생성 승인, 팀 해체 승인 | | | | ✓ |

- 관리자는 22번의 "관리자는 모든 동작 허용" 규칙 하나로 통과한다. 관리자도 같은 판단 관문을 지난다
- SSH 정보를 일반 팀원도 볼 수 있게 한 것은 의도한 결정이다. 팀원이 VM에 접속하려면 필요하기 때문이다

### 2.3 GSMSV 권한이 닿지 않는 곳 (받아들인 한계)

- GSMSV 권한은 **GSMSV 콘솔과 API의 동작만** 막는다. VM 안에서 하는 일은 막지 않는다
- 예: 일반 팀원은 콘솔에서 VM을 끌 수 없지만, VM에 접속한 뒤 VM 안에서 전원을 끄는 명령은 실행할 수 있다
- VM 안에서 계정이 가진 권한으로 하는 일은 GSMSV 권한 밖이다. 팀원끼리 비밀번호를 공유하는 편이 더 편한 경우도 있다. 이 한계는 알고 받아들였다

## 3. 데이터

- **팀**
  - id는 `team-` 뒤에 무작위 12자다. 예: `team-4p8w2k9m1xza` ([23번](resource-naming.md), [상수 값](../constants/resource-id.md))
  - 팀 이름은 사용자가 정한다. 쓸 수 있는 글자, 길이, 겹치면 안 되는 범위, 예약어는 **미정**이다 (백엔드 담당)
  - 상태: 적어도 "관리자 승인 대기", "승인됨", "거절됨", 해체 요청 중을 구분해야 한다. 상태 이름과 칸 구성은 구현할 때 정한다
  - 팀 할당량(CPU·RAM·SSD): 3.4절
- **팀 멤버십**: 사용자와 팀을 잇는다
  - 사용자와 팀은 **N:M**이다. 한 사람이 여러 팀에, 한 팀에 여러 사람이 있을 수 있다
  - 멤버십마다 팀 안의 역할 하나를 가진다
  - **팀장은 한 팀에 한 명**이다. 팀장을 넘길 때도 두 사람의 역할을 한 번에 바꿔서, 팀장이 없거나 두 명인 순간이 생기지 않게 한다
- **초대**: 팀장이 보낸 초대. 대상 계정, 초대 링크에 쓰는 비밀 토큰, 만료, 사용 여부를 가진다. 팀에는 GRN이 없어서 [23번](resource-naming.md)의 하위 자원 표기를 그대로 쓸 수 없다. 초대처럼 팀에 딸린 항목의 형식은 **미정**이다 (백엔드 담당)
- **사용자 id**: `user-` 뒤에 무작위 12자다. 이유: 사용자 id는 GRN의 소유자 칸에 들어간다. 연속된 값이면 가입 순서와 사용자 수가 드러나고, 다른 사람의 id를 추측하기 쉽다
- **VM의 소유자**: 개인(사용자) 아니면 팀, 둘 중 하나다
  - VM 하나는 소유자 하나만 가진다. 팀과 VM은 1:N이다
  - 팀 VM을 만든 사람은 `created_by`에 남는다. 만든 사람이 팀을 나가도 기록은 남고 소유자는 계속 팀이다
  - 팀 VM의 GRN 예: `grn:team-4p8w2k9m1xza:vm-k3m9x2p7q4ta`. 소유자 칸의 팀 id는 사람이 보라고 붙인 표시일 뿐이다. **권한은 반드시 DB에 저장된 소유자로 판단한다**

관계 요약: 사용자 N:M 팀(역할 포함) · 팀 1:N 팀 소유 자원 · 사용자 1:N 개인 소유 자원 · 팀 1:N 초대

## 4. 정책

### 4.1 팀 만들기와 승인

1. 일반 사용자 또는 관리자가 팀 이름을 정해 팀을 만든다
2. 시스템이 팀을 "관리자 승인 대기" 상태로 만들고, **만든 사람을 팀장으로 등록**한다
3. 관리자가 팀을 승인한다. 승인되면 팀 할당량이 적용된다 (3.4절)
4. 승인되면 팀장과 DevOps 엔지니어가 팀 VM을 만들 수 있다

- **승인 대기 중인 팀은 VM을 만들 수 없다.** 승인 대기 중에도 팀원 초대와 팀장 넘기기는 할 수 있다. 승인 대기 팀에서 막는 것은 VM 생성뿐이다
- 관리자가 만든 팀도 관리자 승인을 거친다
- 팀 개수와 팀당 인원에는 제한이 없다
- 만든 사람이 처음 팀장이 되는 이유: 초대는 팀장만 할 수 있어서 누군가는 처음부터 팀장이어야 한다. 실제로 팀을 이끌 사람이 따로 있으면 초대를 마친 뒤 그 사람에게 팀장을 넘긴다
- **승인 거절**
  - 거절 사유를 반드시 적고, 팀장에게 알린다
  - 팀은 "거절됨" 기록으로 남기고 지우지 않는다. 팀장은 고쳐서 다시 신청할 수 있다
  - 거절할 때 이미 들어온 팀원은 그대로 남기고, 수락 전인 초대는 취소한다. 거절된 동안에는 새 초대를 보낼 수 없다
  - 다시 신청하지 않고 방치된 거절 팀을 언제 지울지는 **미정**이다

### 4.2 팀원 초대

정상 흐름

1. 팀장이 초대할 사람의 **학교 이메일 전체**를 정확히 입력한다. 부분 검색, 자동완성, 프로필 카드는 두지 않는다
2. 시스템이 그 이메일로 초대 메일을 보낸다
3. 대상자가 메일의 링크를 누르면 일반 팀원으로 팀에 들어온다. 가입하지 않은 사람은 메일 링크로 처음 로그인하면서 자동으로 가입된다
4. DevOps 역할은 팀장이 따로 부여한다
5. 그 순간부터 대상자의 콘솔에 팀 VM이 나타난다

규칙

- **가입 여부와 관계없이 같은 응답**("초대를 보냈습니다")을 준다. 이유: 응답이 다르면 그 이메일이 가입했는지가 드러난다
- 초대 링크는 보낸 뒤 **7일**이 지나면 만료된다
- 이미 팀원인 사람을 다시 초대하려 하면 "이미 팀원"이라고 알린다
- 초대 링크가 만료됐거나 이미 쓰였으면 요청을 거부한다
- 초대 링크에는 id가 아니라 **별도의 비밀 토큰**을 쓴다. id만 알면 쓸 수 있는 기능은 id가 아니라 비밀 토큰으로 막는다는 원칙 때문이다 ([23번 id 노출 원칙](resource-naming.md))

### 4.3 팀원 제외, 탈퇴, 팀장 넘기기와 승계

- **제외**는 팀장만 한다. 제외된 사람의 콘솔에서 팀 VM이 바로 사라진다. 팀 멤버십을 캐시하지 않으므로([22번](authorization.md)) 제외된 직후의 요청부터 거부된다
- **탈퇴**는 본인이 한다
- 누가 탈퇴하거나 제외되어도 **팀 VM은 삭제되지 않는다.** 그 VM을 만든 사람이 나가도 마찬가지다
- **팀장 넘기기**: 팀장은 팀원 누구에게나(DevOps 엔지니어, 일반 팀원) 팀장을 넘길 수 있다
  1. 팀장이 넘겨받을 팀원을 고른다
  2. 확인 창에서 한 번 더 확인한다. 넘긴 뒤에는 원래 팀장이 되돌릴 수 없고, 되찾으려면 새 팀장이 다시 넘겨 줘야 하기 때문이다
  3. 시스템이 두 사람의 역할을 한 번에 바꾼다. 받는 사람은 팀장이 되고, 원래 팀장은 **일반 팀원**이 된다
  4. 팀원 전원에게 알린다
  - 받는 사람의 수락은 받지 않는다. 관리자 승인도 필요 없다. 관리자도 "관리자는 모든 동작 허용" 규칙으로 넘길 수 있다 (예: 팀장과 연락이 닿지 않을 때)
  - 원래 팀장은 일반 팀원이 되므로 VM 생성·삭제·전원 제어·설정 변경을 더는 할 수 없다. 계속 VM을 관리해야 하면 새 팀장이 DevOps 역할을 준다
  - 권한 변경이므로 감사 로그에 남긴다
  - 팀장이 바뀌어도 팀 VM의 소유자는 팀이므로 GRN은 바뀌지 않는다
- **팀장이 넘기지 않고 탈퇴하면** 시스템이 DevOps 엔지니어 중 한 명을 무작위로 골라 팀장으로 정한다. DevOps 엔지니어가 한 명도 없으면 남은 팀원 중 한 명을 무작위로 정한다
- **마지막 남은 팀원은 탈퇴할 수 없다.** 아무도 관리할 수 없는 팀 VM이 생기기 때문이다. 팀을 없애려면 해체를 요청한다
- **DevOps 역할**: 팀장이 부여한다. 회수는 팀장이 하거나 DevOps 본인이 스스로 내려놓는다
- 팀에서 나간 사람이 전에 알던 VM id나 GRN으로 요청해도 거부된다. 권한 판단이 요청마다 DB에 저장된 소유자와 지금의 멤버십으로 이루어지기 때문이다. id를 안다고 권한이 생기지 않는다. 응답은 **404**다

### 4.4 팀 해체

- 팀장만 해체를 요청할 수 있고, **관리자가 승인해야** 해체된다. 실수로 해체하는 것을 막기 위해서다
- 해체되면 팀 VM은 모두 삭제된다. 팀장 개인 소유로 넘기지 않는다

### 4.5 팀 VM 만들기와 할당량

- 팀 VM은 팀장과 DevOps 엔지니어만 만든다. 승인 대기 중인 팀은 만들 수 없다
- 할당량은 VM 개수가 아니라 CPU·RAM·SSD 할당량으로 센다. 개수로 세면 자원이 많이 필요 없어도 최대 사양으로 여러 대를 만들 수 있다
- 팀 VM은 **만든 사람이 아니라 팀 앞으로** 센다. 팀장이 VM을 만들어도 팀장 개인의 할당량은 줄지 않는다
- **팀 할당량은 모든 팀에 같다: vCPU 8개 · RAM 16 GiB · SSD 60 GiB** (일반 사용자 1인 한도의 2배). 배포 없이 바꿀 수 있는 설정값으로 둔다. 팀 생성이 승인되면 적용된다
- 모든 팀의 VM 할당 합계는 팀 몫(전체에서 운영·서비스 몫을 뺀 뒤 일반 사용자와 50 : 50으로 나눈 절반)을 넘을 수 없다. 그래서 한 팀의 할당량이 남아 있어도 팀 몫 전체가 다 차면 VM을 만들 수 없다 ([할당량](../policies/quota.md))
- 팀 VM 이름
  - 사용자가 정한 이름은 `name`에만 둔다. Proxmox VM 이름 같은 인프라 쪽 이름에는 id(`vm-…`)만 쓴다 ([23번](resource-naming.md))
  - **만든 사람의 이메일이나 이름을 VM 이름·인프라 쪽 이름 어디에도 넣지 않는다.** 팀 VM에 만든 사람의 개인 정보가 남지 않게 하기 위해서다

### 4.6 팀 VM 사용 기간

- **첫 달**은 삭제하지 않는다. 첫 달은 VM마다 그 VM의 생성 시각부터 **31일**이다
- 첫 달이 지나면 **2주마다** 연장 신청을 해야 한다. 연장 신청은 팀원 누구나 할 수 있다
- 연장하지 않으면 만료 즉시 정지 → 3일 유예 → 삭제다. 유예 중에도 연장할 수 있다
- 팀 VM의 연장 신청 시점(만료 며칠 전부터 신청할 수 있는지)은 **미정**이다
- 사용 기간 규칙 전체: [기능별 정책](../policies/feature-policies.md)

### 4.7 알림

- 팀 VM 관련 알림은 팀장, DevOps 엔지니어, 일반 팀원 **모두**에게 보낸다
- 팀장이 바뀌면 팀원 전원에게 알린다
- 알림이 어느 자원의 것인지는 unique resource id로 잇는다. 알림 문구에 VM 이름이 들어 있는지로 판정하지 않는다 (이름은 바뀔 수 있다)

## 5. 하지 않는 것

- 프로젝트 오너 역할을 두지 않는다
- VM 하나를 여러 팀이 함께 소유하지 않는다
- 개인 VM을 팀 VM으로 바꾸지 않는다. 팀 VM을 개인이나 다른 팀으로 옮기는 기능도 두지 않는다. GRN은 소유자가 바뀌지 않는다는 전제로 설계했고, 소유자가 바뀌면 GRN도 바뀌기 때문이다
- 팀을 해체할 때 팀 VM을 팀장 개인에게 넘기지 않는다. 모두 삭제한다
- 팀원 한 명이 나갔다고 팀 VM을 지우지 않는다
- VM 안의 동작을 GSMSV 권한으로 막지 않는다
- 팀 개수와 팀당 인원을 제한하지 않는다
- 팀 VM 이름이나 인프라 쪽 이름에 만든 사람의 이메일이나 이름을 넣지 않는다
- 팀 멤버십을 캐시하지 않는다 ([22번](authorization.md))
- 팀장을 두 명 이상 두지 않는다. 팀장을 넘길 때 받는 사람의 수락이나 관리자 승인을 받지 않는다
- 초대할 때 이메일 부분 검색이나 자동완성, 프로필 카드를 두지 않는다

## 6. 완료 판정

- 팀장이 초대한 사람이 메일의 링크를 누르면, 그 사람의 콘솔에 팀 VM이 나타난다
- 팀장이 제외한 사람은 바로 다음 요청부터 팀 VM을 볼 수도, 조작할 수도 없다. 콘솔에서 사라지고, 전에 알던 GRN으로 요청해도 404를 받는다
- 일반 팀원은 팀 VM을 보고, SSH 정보를 확인하고, 연장을 신청할 수 있다. 생성·삭제·전원 제어·설정 변경을 요청하면 403을 받는다
- 팀장이 다른 팀원에게 팀장을 넘기면, 받는 사람은 바로 팀장 권한을 갖고 원래 팀장에게는 일반 팀원 권한만 남는다. 어느 순간에도 팀장은 한 명이다
- 팀장이 넘기지 않고 탈퇴하면 규칙대로 새 팀장이 정해지고, 팀 VM은 그대로 남는다
- 승인 대기 중인 팀은 VM을 만들 수 없다. 해체는 관리자 승인 뒤에만 되고, 그때 팀 VM이 모두 삭제된다
- 팀 VM은 팀 할당량과 팀 몫 안에서만 만들어지고, 만든 사람 개인의 할당량을 쓰지 않는다

## 7. 정하지 않은 것

| 항목 | 정하는 사람 |
|---|---|
| 팀 이름 규칙(글자, 길이, 겹치면 안 되는 범위, 예약어)과, 이름이 겹칠 때 그 사실을 알려 줄지 | 백엔드 담당 |
| 초대처럼 팀에 딸린 항목의 형식 | 백엔드 담당 |
| 방치된 거절 팀을 언제 지울지 | 미정 |
| 팀 VM의 연장 신청 시점 | 미정 |
| 팀 쪽 API 구조(팀 만들기·초대·제외 등의 URL과 요청·응답 형식) | 백엔드·프론트엔드 담당 |
