# 22번(권한 판단 Layer) — 모든 요청을 한 곳에서 판단한다

> 읽는 사람: GSMSV v2를 개발하는 사람(Kotlin API, Go 인프라 연동, React). 이 문서만 읽고 구현할 수 있게 이유와 하면 안 되는 것까지 적었다.
>
> 함께 읽을 문서: [21번(팀과 역할)](team-ownership.md) · [23번(자원 이름 규칙)](resource-naming.md)
>
> 표기: **확정**은 정한 내용, **개발 중 결정**은 원안은 있지만 개발하면서 확정하기로 한 내용, **미정**은 아직 정하지 않은 내용이다. 9장 "개발 중 결정"과 13장 "정하지 않은 것"을 뺀 나머지는 모두 확정이다.

## 1. 무엇을 하는 기능인가

모든 요청을 한 곳에서 **"누가, 무엇을, 어느 자원에"** 세 요소로 판단하고, 등록한 규칙에 맞지 않으면 **기본으로 거부**한다.

- 권한 검사를 기능마다 복사해 붙이면 검사가 곳곳에 흩어지고, 새 기능을 만들 때 검사를 빠뜨리기 쉽다. 기본값이 "허용"이면 검사가 빠져도 아무 일도 일어나지 않아서 빠진 줄 모른다
- 그래서 판단하는 곳을 하나로 모으고, 기본값을 "허용"에서 "거부"로 한다. 명시적으로 허용한 것만 통과한다
- 거부 응답도 규칙 없이 403과 404를 섞어 쓰면 안 된다. 규칙을 하나로 정한다 (7장)

## 2. 용어

| 용어 | 뜻 |
|---|---|
| 자원 로더 | 자원을 DB에서 불러오는 함수. 권한 판단을 이 함수 안에서 한다. 이 함수를 거치지 않으면 자원 객체를 손에 넣을 수 없다 |
| `authorize()` | 판단 함수. (누가, 무엇을, 어느 자원에)를 받아 규칙표와 대조한다 |
| 규칙표 | (역할, 동작) → 허용 여부 |
| 동작 이름 | 예: `vm.delete`, `team.invite`, `snap.create`. 앞부분은 자원 id 접두사와 같게 쓴다 (`vm-` ↔ `vm.delete`) |
| GRN | 서비스 자원을 가리키는 이름 `grn:{소유자 id}:{자원 id}` ([23번](resource-naming.md)) |

## 3. 누가 판단받는가

- **사용자**: 전역 역할(일반 사용자, 관리자)과, 자원이 팀 것이면 그 팀에서의 역할(팀장, DevOps 엔지니어, 일반 팀원)로 판단받는다
- **관리자**: 다른 주체와 같은 판단 지점을 지나고, "관리자는 모든 동작 허용" 규칙 하나로 통과한다 (6장)
- **시스템(`SYSTEM`)**: 만료 처리, 자동 스냅샷 같은 백그라운드 동작을 하는 가상 주체다 (개발 중 결정, 9장)
- **판단하는 곳은 Kotlin API 서버의 자원 로더뿐이다.** Go 인프라 실행 엔진에는 권한 판단 코드를 두지 않는다

## 4. 판단의 입력과 순서

### 4.1 입력: 누가, 무엇을, 어느 자원에

- 판단 함수 하나(`authorize()`)가 요청마다 자원의 소유자(개인 또는 팀)와, 팀이면 그 팀에서 요청자의 역할을 확인하고, 역할별 규칙표와 대조한다
- 전역 역할만으로는 판단할 수 없다. 같은 사람이 팀 A에서는 팀장, 팀 B에서는 일반 팀원일 수 있기 때문이다
- "어느 자원에"는 [23번](resource-naming.md) 형식으로 받는다

| 대상 | 형식 | 예 |
|---|---|---|
| 서비스 자원 | GRN | `grn:team-4p8w2k9m1xza:vm-k3m9x2p7q4ta` |
| 하위 자원 | `{부모 GRN}/{하위 자원 id}` | `grn:team-4p8w2k9m1xza:vm-k3m9x2p7q4ta/snap-7qz3m8k2` |
| 팀 대상 동작 | 팀 id | `team-4p8w2k9m1xza` |

- 요청에서 대상 자원을 특정할 수 없으면 **거부**한다. 자원을 모른 채 통과시키지 않는다

### 4.2 순서: 소유 먼저 → 역할 → 규칙표

1. 자원이 개인 것인지 팀 것인지 확인한다 (DB에 저장된 소유자)
2. 팀 것이면 그 팀에서 요청자의 역할(팀장·DevOps·일반)을 구한다
3. 규칙표와 대조한다

- **팀 멤버십은 캐시하지 않는다.** 캐시하면 팀에서 제외된 사람이 몇 분 동안 계속 접근할 수 있다. 멤버십을 요청마다 읽어도, 로더가 자원을 한 번만 읽으므로 전체 조회 수는 크게 늘지 않는다

## 5. 판단하는 위치: 두 층

### 5.1 선언 — 컨트롤러 애너테이션

- 컨트롤러 메서드마다 권한 애너테이션(예: `@RequirePermission("vm.delete")`)을 붙여, 그 엔드포인트가 무슨 동작을 하는지 적는다
- **애너테이션이 없는 컨트롤러 메서드가 하나라도 있으면 앱이 시작되지 않게 막는다.** 규칙을 등록하지 않은 새 기능이 아무 요청도 통과시키지 못하게 하는, 기본값 거부의 장치다. 개발 중에 바로 드러나며, 이것이 의도한 동작이다

### 5.2 판단 — 자원 로더 한 곳

- 실제 판단은 자원을 불러오는 함수(자원 로더) 하나에서만 한다. 예: `vmAccess.load(grn, user, "vm.delete")`
- 로더를 거치지 않으면 자원 객체를 손에 넣을 수 없게 만든다. 그래서 검사를 빠뜨리는 것이 구조적으로 불가능하다
- 로더는 자원을 DB에서 **한 번만** 읽고, 그 한 줄로 소유 판단까지 한다. 권한 판단 때문에 같은 자원을 두 번 읽지 않는다
- **목록 조회**는 같은 규칙표를 쓰는 짝 함수(예: `listVisible(user)`)로 처리한다. 단건 판단과 목록이 어긋나지 않게 하기 위해서다

### 5.3 로더는 세 가지다

| 로더 | 받는 것 | 하는 일 |
|---|---|---|
| **서비스 자원 로더** | GRN | ① GRN 파서로 문자열 전체를 검사하고 자원 id만 꺼낸다 ② 그 id로 DB에서 자원을 읽는다 ③ DB 값(소유자, id)으로 GRN을 다시 만들어 받은 문자열과 **통째로 비교**한다. 다르면 404다 ④ DB의 소유자와 요청자의 팀 역할로 규칙표를 판단한다 |
| **하위 자원 로더** | 부모 GRN + 하위 자원 id | ① 부모 GRN으로 서비스 자원 로더의 ①~④를 그대로 거친다 ② 하위 id로 하위 자원을 찾는다 ③ 그 하위 자원의 실제 부모가 요청에 적힌 부모와 같은지 확인한다. 다르면 404다 |
| **팀 전용 로더** | 팀 id | 팀은 GRN이 없으므로 팀 대상 동작(예: `team.invite`)은 팀 전용 로더로 판단한다 |

- 하위 자원 로더는 **부모 GRN 없이는 부를 수 없게 함수 서명으로 강제**한다. 예: `snapshotAccess.load(parentGrn, snapshotId, user, "snap.delete")`. 부모 없이 하위 id만으로 찾는 길은 만들지 않는다. 식별값의 일부만으로 찾다가 다른 자원을 잡는 사고를 막기 위해서다
- 팀 전용 로더도 같은 `authorize()` 규칙표와 같은 감사 로그를 거친다. 로더마다 판단 기준이 달라지면 안 된다

### 5.4 GRN의 소유자 칸으로 판단하지 않는다 (가장 중요한 규칙)

권한은 **항상 DB에 저장된 소유자**로 판단한다. GRN 안의 소유자 칸은 사람이 읽으라고 붙인 표시일 뿐이다. GRN은 사용자가 요청에 담아 보내는 문자열이라 누구나 고칠 수 있기 때문이다.

**잘못 쓴 예**

1. 공격자 A(`user-aaaa…`)가 로그나 스크린샷에서 남의 VM id `vm-k3m9…`를 알게 된다
2. A가 소유자 칸만 자기 것으로 바꿔 `grn:user-aaaa…:vm-k3m9…` 삭제를 요청한다
3. 서버가 소유자 칸을 믿고 "요청자 본인의 VM"이라고 판단하면 **남의 VM이 지워진다**

**막는 방법**

- GRN 파서는 자원 id만 돌려주고 소유자 칸 값은 파서 밖으로 꺼내지 않는다. 판단에 잘못 쓰이는 것을 코드 구조로 막는 장치다
- 로더의 ③번 비교: DB 값으로 GRN을 다시 만들어 통째로 비교하므로 소유자 값을 따로 꺼내지 않는다. 소유자 칸이 DB와 다르면 404다
- 비유: 소유자 칸은 택배 상자에 붙은 이름표이고, DB의 소유자는 등기부다. 이름표는 누구나 고쳐 쓸 수 있으니 문지기는 등기부를 본다

## 6. 관리자

- `관리자면 통과` 같은 우회 코드를 두지 않는다
- 관리자도 같은 판단 지점을 지나고, "관리자는 모든 동작 허용" 규칙 하나로 통과한다
- 관리자가 한 일도 판단 기록에 남는다
- "모든 자원에 모든 동작"처럼 범위가 넓은 규칙은 이 관리자 규칙 하나뿐이다. 다른 역할에는 두지 않는다

## 7. 거부를 알리는 방법: 404와 403

| 상황 | 응답 | 예 |
|---|---|---|
| 볼 수 없는 자원 (없거나, 있어도 요청자와 관계가 없다) | **404** | 팀 밖 사람이 팀 A의 VM을 조회하거나 조작 |
| 볼 수는 있지만 그 동작 권한이 없다 | **403** | 팀 A의 일반 팀원이 팀 A의 VM을 삭제 |
| 받은 GRN의 소유자 칸이 DB의 소유자와 다르다 | **404** | 5.4의 잘못 쓴 예 |

- 403에는 **필요한 역할과 요청자의 역할**을 함께 알려 준다. 문구 예: "팀장 또는 DevOps만 삭제할 수 있습니다. 내 역할: 일반 팀원"
- 판단은 역할 조회 한 번으로 세 갈래(404 / 403 / 허용)로 나뉜다. 팀원이면 누구나 조회할 수 있으므로 "볼 수 있나"는 "역할이 있나"와 같은 질문이다
- 소유자 칸이 틀린 GRN이 403이 아니라 404인 이유: 볼 수 없는 자원은 404로 숨기는 규칙을 따르기 때문이다
- 모든 에러 응답은 공통 형식 **`{code, message, request_id}`**로 보낸다
- **에러 메시지에는 요청자가 보내지 않은 다른 자원의 존재나 id를 담지 않는다.** 사용자 문의가 오면 관리자는 `request_id`로 서버 기록을 찾는다
- GRN 형식이 틀리면 파서가 거절한다. 이때의 응답 코드는 **미정**이다 (API 구조를 정할 때 함께 정한다)

## 8. 규칙표

처음 들어갈 내용은 [21번](team-ownership.md)에서 정한 것이다.

| 대상 | 허용 |
|---|---|
| 팀 자원 — 팀원 누구나 (팀장·DevOps·일반) | 조회, SSH 접속 명령어와 비밀번호 보기, 사용 기간 연장 신청 |
| 팀 자원 — 팀장·DevOps | 생성, 삭제, 전원 제어, 사양 변경, 스냅샷, 포트포워딩, 방화벽, HTTPS 도메인 연결 |
| 팀 — 팀장만 | 팀원 초대·제외, DevOps 역할 부여, 팀 해체 요청, 팀장 넘기기 |
| DevOps 역할 회수 | 팀장, 또는 DevOps 본인 |
| 관리자 | 모든 자원에 모든 동작 |
| `SYSTEM` | 내부 동작 전용 규칙 (만료 처리, 자동 스냅샷 등). 목록은 동작 이름과 함께 정한다 |
| 개인 자원 | 소유자 본인이 그 자원의 모든 동작 (**확인 필요**: 따로 정하지 않은 기본 가정이다. 13장) |

## 9. 개발 중 결정 (원안)

아래는 원안이 있지만 **개발하면서 확정하기로** 한 부분이다. 원안은 참고하되 확정으로 쓰지 않는다.

- **프론트엔드가 권한을 아는 방법 (원안)**: API 응답에 그 자원에 대해 요청자가 할 수 있는 동작 목록을 함께 내려 준다. 예: `permissions: { delete: false, power: false, extend: true }`. 프론트는 역할 규칙을 복제하지 않고 **버튼을 숨기는 데만** 쓴다. 실제 차단은 항상 서버가 한다. 화면에서 버튼을 숨기는 것은 서버 검증을 대신하지 않는다
- **거부 로그와 감사 로그 (원안)**: 거부 전부와 민감한 허용(삭제, 비밀번호 조회, 권한 변경)을 DB 감사 테이블에 남긴다. 칸은 요청 ID, 누가, 무엇을, 어느 자원에, 역할, 이유 코드다. 나머지 일반 동작은 구조화 로그로 남기고, Kotlin이 Go를 호출할 때 같은 요청 ID를 넘겨 두 서비스의 로그를 묶는다
  - 이유 코드 예(서버 기록용): `RESOURCE_NOT_FOUND`(정말 없음), `NO_RELATION`(있지만 요청자와 관계없음), `ROLE_LACKS_ACTION`(역할에 그 동작 권한이 없음), `TEAM_NOT_APPROVED`(팀이 승인 대기 중). 밖에는 403과 404로만 보여도 서버는 원인을 구별해야 관리자가 요청 ID로 바로 원인을 찾는다
  - 비밀번호 값 자체는 어디에도 기록하지 않는다. 조회했다는 사실만 남긴다
  - 감사 로그의 "어느 자원에" 칸은 서비스 자원 GRN, 하위 자원 표기, 사용자·팀 id를 모두 받을 수 있어야 한다
  - 보존 기간은 90일을 제안한다
  - 로그, 감사 로그, 운영 리포트는 개발진만 볼 수 있다. 개발진에서 빠지는 사람은 그 접근도 함께 회수한다
- **규칙을 두는 곳 (원안)**: Kotlin 코드에 둔다 (enum과 `when` 매핑). 역할이 다섯 개뿐이고 자주 바뀌지 않으며, 새 동작을 추가하고 규칙을 적지 않으면 컴파일이 안 되게 만들 수 있다. 규칙 변경이 git 이력에 남고 테스트로 잠글 수 있다. 팀마다 다른 권한이 필요해지면 그때 DB로 옮긴다
- **시스템 자동 동작 (원안)**: `SYSTEM` 가상 주체를 두고, 만료 처리와 자동 스냅샷 같은 백그라운드 동작도 같은 `authorize()`를 지나게 해 기록에 남긴다. 스케줄러는 Kotlin에 둔다. Kotlin 서버를 여러 개 띄우면 같은 작업이 중복 실행되므로 분산 락이 필요하다 (방법은 PostgreSQL advisory lock을 제안)
- **구현할 때 조심할 곳 (제안)**: 목록 조회 필터(`listVisible`)와 단건 판단(로더)이 어긋나는 것이 가장 흔한 권한 버그다. 둘이 같은 규칙표를 쓰게 만들고 함께 검증하는 테스트를 둔다. 로더를 우회해 저장소를 직접 부르는 코드가 생기지 않게, 구조 테스트로 "컨트롤러는 저장소를 직접 부를 수 없다"를 강제한다

## 10. 하지 않는 것

- 기능 코드 안에 개별 권한 검사를 두지 않는다. 판단 지점의 결론과 다른 개별 검사는 제거 대상이다. 판단은 한 곳에서만 한다
- `관리자면 통과` 같은 우회 경로를 두지 않는다
- 프론트가 역할 규칙을 복제해 판단하지 않는다. 버튼을 숨기는 것이 차단은 아니다
- 팀 멤버십을 캐시하지 않는다
- GRN의 소유자 칸 값으로 판단하지 않는다. GRN을 `split(":")` 같은 방식으로 직접 자르지 않고 파서만 쓴다
- 부모 없이 하위 자원 id만으로 하위 자원을 찾지 않는다
- 로더마다 다른 규칙으로 판단하지 않는다
- 규칙을 DB에 두지 않는다 (팀별 권한이 필요해지기 전까지)
- 비밀번호 값을 로그에 남기지 않는다
- Go 인프라 서비스에서 권한을 판단하지 않는다
- 에러 메시지에 요청자가 보내지 않은 다른 자원의 존재나 id를 넣지 않는다

## 11. 코드 리뷰 항목

v2 저장소의 PR 템플릿(`.github/pull_request_template.md`)에 아래 두 줄이 들어 있다. PR마다 확인한다.

```text
- [ ] 권한 판단을 자원 로더 밖에서 하지 않았다 (22번 권한 판단 Layer)
- [ ] GRN 문자열을 직접 자르지 않고 GRN 파서만 썼다. GRN의 소유자 칸 값을 어떤 판단에도 쓰지 않았다 (23번 자원 이름 규칙)
```

## 12. 완료 판정

- 권한 판단이 한 곳(자원 로더와 `authorize()`)에서만 일어난다. 기능 코드에 복사된 개별 권한 검사가 없다
- 권한 애너테이션이 없는 엔드포인트가 있으면 앱이 시작되지 않는다. 규칙을 등록하지 않은 새 동작은 아무 요청도 통과시키지 못한다
- 모든 판단이 누가·무엇을·어느 자원에로 이루어지고, 대상 자원은 23번 형식(서비스 자원 GRN, 하위 자원 `{부모 GRN}/{하위 자원 id}`, 팀 id)으로 특정된다
- 타인 자원에 대한 거부 응답이 모든 기능에서 같다: 볼 수 없으면 404, 볼 수 있지만 권한이 없으면 403
- GRN의 소유자 칸만 바꿔 보낸 요청이 404로 거부된다
- 인증 수단이 없거나 규칙이 등록되지 않은 요청이 기본 거부에 걸린다
