# 웹 API 명세가 지켜야 할 규칙

> 웹 API(Client ↔ Server)를 명세하는 사람이 21번(팀과 역할)·22번(권한 판단)·23번(자원 이름 규칙) 중에서 **API에 걸리는 규칙**만 모아 본 점검표다. 원본은 각 규칙 문서이고, 요약과 원본이 다르면 원본이 맞다.
>
> 관련 문서: [21번](team-ownership.md) · [22번](authorization.md) · [23번](resource-naming.md)

## 1. 명세를 쓰는 방식

- 웹 API 명세는 **OpenAPI** 형식으로 이 저장소에 쓴다
- **계약 먼저**: API를 새로 만들거나 바꿀 때는 구현보다 이 저장소의 명세 PR을 먼저 올린다
- 이 저장소는 공개 저장소다. 명세에 **실제 서버 주소, 내부 IP, 노드·장비 이름, 실제 도메인, 실제 학번·이메일, 비밀값을 쓰지 않는다.**
  - OpenAPI의 `servers` 항목에는 실제 주소 대신 `https://{host}` 같은 자리표시를 쓴다
  - 예시 값(`example`)에는 `example.com`, `user-aaaaaaaaaaaa` 같은 가짜 값을 쓴다
- 내부 API(Server ↔ Infra)는 이 점검표의 범위가 아니다. 책임 나눔은 [Kotlin·Go 경계](../policies/kotlin-go-boundary.md)에 있다

## 2. 점검표

### 2.1 권한과 에러 (22번)

| 영역 | 규칙 |
|---|---|
| 권한 | 권한은 DB에 저장된 소유자로만 판단한다. GRN의 소유자 칸은 어떤 판단에도 쓰지 않는다. 소유자 칸이 DB와 다른 GRN은 404로 거절한다 |
| 권한 | 권한 판단은 자원 로더 한 곳에서만 한다. 목록은 같은 규칙을 쓰는 짝 함수로 처리한다 |
| 거부 | 볼 수 없는 자원은 **404**, 볼 수는 있지만 권한이 없는 동작은 **403**. 관리자도 같은 관문을 지난다 |
| 에러 | 모든 에러는 `{ code, message, request_id }` 형식이다. 403에는 필요한 역할과 요청자의 역할을 알려 준다 |
| 에러 | 에러 메시지에 요청자가 보내지 않은 다른 자원의 존재나 id를 넣지 않는다 |
| 응답 | 자원 응답에 그 사용자가 할 수 있는 동작을 `permissions`로 함께 준다 (예: `{ delete: false, extend: true }`). 프론트는 버튼을 숨기는 데만 쓴다. 이 부분은 **개발 중 결정**이다 ([22번 9장](authorization.md)) |

### 2.2 자원 지정과 id (23번)

| 영역 | 규칙 |
|---|---|
| 자원 지정 | 서비스 자원(VM·함수·데이터베이스·앱)은 GRN `grn:{소유자 id}:{자원 id}`로 가리킨다 |
| 자원 지정 | 하위 자원(스냅샷·포트포워딩·도메인·방화벽 규칙·트리거·버전·백업·서비스·환경·배포 기록)은 `{부모 GRN}/{하위 id}`로 가리킨다. **부모 GRN 없이 하위 id만으로 찾는 API는 만들지 않는다** |
| id | 사용자·팀 id는 `user-…`·`team-…`(접두사 + 무작위 12자)다. 하위 id는 접두사 + 8자다. 글자는 소문자·숫자이며 `i`·`l`·`o`·`u`는 쓰지 않는다. 형식이 맞지 않으면 거절한다 ([상수 값](../constants/resource-id.md)) |
| 응답 | 사용자가 정한 이름은 `name` 칸이고 바꿀 수 있다. GRN에는 들어가지 않는다 |
| 응답 | 노드·VM 번호 같은 **구현 값은 응답에 넣지 않는다.** 노드 정보는 관리자 화면에서만 보인다 |
| 응답 | 상세 조회는 GRN 하나로 서비스 정보와 하위 자원 목록(각 id 포함)을 한 번에 준다. 하위 자원만 따로 받는 목록 API도 둔다. 값을 콜론으로 이어 붙인 문자열은 쓰지 않는다 |
| 공개 기능 | id만 알면 쓸 수 있는 기능(공개 호출 주소, 초대 링크 등)은 id가 아니라 별도 비밀 토큰으로 막는다 |

### 2.3 팀 (21번)

| 영역 | 규칙 |
|---|---|
| 소유자 | 소유자는 개인 또는 팀 하나다. VM은 한 팀에만 속하고, 개인 VM을 팀 VM으로 바꿀 수 없다 |
| 역할 | 전역 역할은 USER·ADMIN, 팀 역할은 팀장·DevOps·일반 팀원이다 |
| 승인 | 승인 대기 중인 팀은 VM을 만들 수 없다 (팀 초대와 팀장 넘기기는 할 수 있다) |

## 3. 명세가 정하게 되는 항목 (백엔드·프론트엔드 담당)

아래는 규칙 문서가 정하지 않고 API 명세를 쓰면서 정하기로 한 항목이다. 정한 결과를 명세에 쓰고, 백엔드와 프론트엔드가 합의했는지 PR에서 확인한다.

- URL에 GRN을 넣는 방법 (GRN에는 `:`, 하위 자원 표기에는 `/`가 들어 있다)
- `permissions` 키 형식(`delete` / `vm.delete`)과 동작 이름 목록. 앞부분은 자원 접두사와 같게 쓴다 (`vm.`, `snap.`, `team.`)
- 공통 에러 `code` 값의 목록, 형식 검사 실패의 응답 코드
- 목록 조회의 페이지 나누기 방식

백엔드 단독으로 정하는 항목(사용자가 정하는 이름 규칙과 예약어, 이름이 겹칠 때 알려 줄지, 팀 초대 같은 팀 쪽 항목의 형식, 삭제된 자원 행 보존, GRN의 DB 저장 여부, id 노출 원칙의 적용 범위)도 명세에 드러날 수 있다. 목록은 [23번 12장](resource-naming.md)에 있다.

## 4. 아직 정하지 않은 것 (이 저장소의 운영)

- 다른 저장소로 계약을 전달하는 방법, 생성한 코드를 커밋할지, 버전 태그 규칙, 깨지는 변경의 처리
- 이 저장소의 `develop`에서 API 변경을 승인하는 규칙
- Server ↔ Infra 사이 형식(REST + OpenAPI 또는 gRPC)
