# 23번(자원 이름 규칙 통일) — GRN과 id

> 읽는 사람: GSMSV v2를 개발하는 사람(Kotlin API, Go 인프라 연동, React). 이 문서만 읽고 구현할 수 있게 이유·하면 안 되는 것·예시까지 적었다. 이 규칙을 잘못 구현하면 **남의 자원이 지워지는 보안 사고**로 이어질 수 있다.
>
> 함께 읽을 문서: [21번(팀과 역할)](team-ownership.md) · [22번(권한 판단)](authorization.md) · [상수 값](../constants/resource-id.md)
>
> 표기: 따로 표시가 없으면 **확정**이다. 아직 정하지 않은 것은 **미정**이라고 적고, 정하는 담당을 함께 적었다.

## 1. 이름과 범위

- 이름은 **GRN (GSMSV Resource Name)** 이다. AWS ARN과 비슷하게 만들었지만 헷갈리지 않도록 ARN이라 부르지 않는다
- 사용자는 GRN을 볼 수 있다. 평소에는 자기가 정한 이름으로 서비스를 쓴다
- **GRN을 가지는 것은 서비스 자원 4종뿐이다**: VM, 서버리스 함수, 데이터베이스, 원터치 배포(앱)
  - 사용자와 팀은 GRN 없이 각자의 id만 가진다
  - 하위 자원(스냅샷, 포트포워딩, HTTPS 도메인 연결, 트리거 등)은 서비스의 하위이므로 GRN이 아니라 다른 형식(5장)을 쓴다
  - 이유: AWS가 IAM 사용자에게도 ARN을 주는 것은 권한 정책 문서에 "누가"를 ARN으로 적기 때문이다. GSMSV는 역할 규칙표로 판단하므로 사용자·팀을 GRN으로 가리킬 일이 없다
  - 따라오는 것: 팀을 대상으로 하는 동작(팀 초대 등)은 서비스 자원용 로더가 아니라 팀 전용 로더로 판단한다. 감사 로그의 "대상" 칸은 GRN, 하위 자원 표기, 사용자·팀 id를 모두 받을 수 있어야 한다
- **모든 서비스 자원이 같은 형식을 쓴다.** 서비스별로 나누지 않고 전체 서비스에서 유일하다. 큰 클라우드가 아니라 교내 서비스이기 때문이다
- **사람이 정한 이름은 GRN에 넣지 않는다.** 이름(`name`)은 바꿀 수 있고, id와 GRN은 바뀌지 않는다
- **노드(위치)는 GRN에 넣지 않는다.** 내부적으로는 노드가 나뉘어 있지만 사용자는 노드가 하나인 것처럼 쓴다. 노드는 시스템이 자동으로 배분한다
- **소유 단위(개인 또는 팀)는 GRN에 넣는다**
- 사양, 노드, VM 번호, 만든 사람은 GRN이 아니라 공통 자원 모델·서비스별 모델·구현 층에 둔다

## 2. id 규칙

- 이름은 **unique resource id**다
- **값은 순수 랜덤이다.** ULID처럼 생성 시각을 담거나 순서대로 커지는 방식은 쓰지 않는다. 앞 부분이 생성 시각이면 언제 만들었는지 드러나고, 순서대로 커지면 다음 id를 추측할 수 있다. 둘 다 "추측하기 어렵게"와 부딪힌다
- **모양은 `{접두사}-{무작위 부분}`이고, 소문자·숫자·하이픈만 쓰며, 자원 종류 접두사로 시작한다.** 예: `vm-k3m9x2p7q4ta`
  - 이유: Kubernetes 이름 규칙(소문자·숫자·`-`, 알파벳으로 시작, 63자 이하)과 Proxmox VM 이름 규칙에 그대로 쓸 수 있어야 한다. 밑줄(`_`) 같은 글자는 한쪽에서 실패할 수 있다. "알파벳으로 시작" 조건은 접두사가 채워 준다
- 무작위 부분에 쓰는 글자는 **32개**다 (`i`, `l`, `o`, `u` 제외). 길이는 서비스 자원·사용자·팀 12자, 하위 자원 8자다. 값은 [상수 값](../constants/resource-id.md)에 있다
- **id는 전역에서 유일하다.** GRN 안의 unique resource id가 GRN이 전역에서 유일함을 보장한다
- **겹치면 서버가 id를 다시 뽑아 재시도한다. 사용자에게 실패를 돌려주지 않는다.**
  - 지금 사용 중인 값과는 겹치면 안 된다. 삭제된 자원과 같은 값이 다시 생기는 것은 막지 않는다
  - 이유: ① 겹쳤다는 사실을 알리면(생성 실패, 재사용 거부) 그 값을 가진 자원이 있거나 있었다는 사실이 드러난다 ② 삭제된 값 목록을 영원히 보관할 필요가 없다 ③ 경우의 수가 크면 같은 값이 다시 나올 확률이 거의 0이다
- **난수는 암호학적 난수 생성기로 만든다.** Kotlin `SecureRandom`, Go `crypto/rand`. `Random`·`math/rand`는 쓰지 않는다
- 사용자·팀 id도 같은 규칙이다: `user-8hq2m5v7c3kx`, `team-4p8w2k9m1xza`. 연속된 값은 id로 쓰지 않는다 (가입 순서와 사용자 수가 드러나고 추측하기 쉽기 때문이다)
- 접두사 목록, 정규식, 생성 길이는 **한 파일에서 관리하고, 그 파일로 Kotlin·Go·React용 상수를 만든다.** 세 언어가 값을 각자 들고 있으면 한쪽만 바뀌어 어긋난다 (파일 형식과 만드는 방법은 미정, [상수 값](../constants/resource-id.md))

## 3. GRN 형식과 소유자 칸

- **GRN은 `grn:{소유자 id}:{unique resource id}` 세 칸으로 고정한다**
  - 예: `grn:team-4p8w2k9m1xza:vm-k3m9x2p7q4ta`, `grn:user-8hq2m5v7c3kx:fn-6d2r8t5y3n7e`
  - 구분자는 `:`다. id 안에는 `:`가 나오지 않으므로 `:`로 나누면 세 칸이 정확히 나온다
  - **서비스 칸은 두지 않는다.** AWS ARN의 서비스 칸은 권한 정책의 와일드카드에 쓰이는데, GSMSV는 역할 규칙표로 판단하므로 쓸 곳이 없다. 자원 종류는 id 접두사가 알려 준다
  - 소유자 칸에는 사용자 id(`user-…`) 또는 팀 id(`team-…`)가 들어간다
- **소유자 칸은 표시용이다. 권한 판단은 항상 DB에 저장된 소유자로 한다.**
  - 사람이 읽을 때는 쓴다: 감사 로그에 `grn:team-4p8w…:vm-k3m9… 삭제됨`이 찍혀 있으면, 관리자는 DB를 열지 않고도 어느 팀의 자원인지 안다
  - 서버가 요청을 허락할지 판단할 때는 쓰지 않는다
  - 이유: GRN은 사용자가 요청에 담아 보내는 문자열이라 누구나 고칠 수 있다. 공격자 A(`user-aaaa…`)가 로그나 스크린샷에서 남의 VM id `vm-k3m9…`를 알게 되고, 삭제 요청에 `grn:user-aaaa…:vm-k3m9…`라고 소유자 칸만 자기로 바꿔 보낸다. 서버가 소유자 칸을 믿으면 남의 VM이 지워진다
  - 비유: 소유자 칸은 택배 상자에 붙은 이름표이고, DB의 소유자는 등기부다. 이름표는 누구나 고쳐 쓸 수 있으니 문지기는 등기부를 본다
- **GRN 파서는 unique resource id만 돌려준다.** 소유자 칸의 값은 파서 밖으로 꺼내지 않는다. 소유자 칸이 판단에 잘못 쓰이는 것을 코드 구조로 막는 장치다
- **소유자 칸이 DB의 소유자와 다른 GRN이 들어오면 404로 거절한다**
  - 방법: 자원 로더가 id로 읽은 DB 값(소유자, id)으로 GRN을 다시 만들어, 받은 문자열과 통째로 비교한다. 소유자 값을 따로 꺼내지 않으므로 "파서는 id만 돌려준다"와 충돌하지 않는다
  - 이유: 한 자원을 가리키는 GRN 문자열은 하나뿐이어야 로그·검색에서 헷갈리지 않는다. 틀린 GRN이 그대로 통과되면 버그가 늦게 드러난다. 403이 아니라 404인 것은 볼 수 없는 자원은 404로 숨기는 규칙([22번](authorization.md))을 따르기 때문이다
- **받아들인 단점**: 소유자가 바뀌면 GRN도 바뀐다. [21번](team-ownership.md)에서 소유자 이전을 하지 않기로 했으므로 지금 정책과는 맞다. 내부를 id로 이어 두면 나중에 이전을 허용해도 DB 연결은 깨지지 않고 GRN 문자열만 달라진다. DB 조회가 늘지는 않는다. 소유자 칸이 없어도 서버는 어차피 id로 자원 한 줄을 읽는다

## 4. 요청이 들어왔을 때

**서비스 자원 요청**

1. GRN에서 unique resource id만 꺼낸다 (파서가 문자열 전체를 엄격한 정규식으로 검사하고, 통과하지 못하면 거절한다)
2. 그 id로 DB에서 자원 한 줄을 읽는다. 소유자는 DB에 저장된 값이다
3. DB 값(소유자, id)으로 GRN을 다시 만들어 받은 문자열과 통째로 비교한다. 다르면 404다
4. DB의 소유자와 요청자의 역할로 허용 여부를 판단한다 ([22번](authorization.md)). 볼 수 없으면 404, 볼 수는 있지만 권한이 없으면 403이다

**하위 자원 요청**

1. 첫 `/`에서 잘라 부모 GRN과 하위 자원 id로 나눈다
2. 부모 GRN으로 위 1~4를 그대로 거친다
3. 하위 자원 id로 하위 자원을 찾는다
4. 그 하위 자원의 실제 부모가 요청에 적힌 부모와 같은지 확인한다. 다르면 404다

**팀 대상 요청**은 팀 전용 로더로 판단한다.

## 5. 하위 자원

- **하위 자원은 GRN과 공통 자원 행이 없다. 자기 id만 가진다**
- **id 모양**: `{하위 종류 접두사}-{무작위 8자}`. 글자 규칙은 서비스 자원과 같고, 전역에서 유일하다
  - 전역에서 유일하게 하는 이유: 포트 규칙, 프록시 라우트처럼 모든 VM이 함께 쓰는 한 공간에서는 식별값이 겹치면 안 된다. 또 코드가 실수로 부모 없이 하위 id만으로 찾더라도 엉뚱한 자원을 잡지 않는다
- **표기(화면·로그·API): `{부모 GRN}/{하위 자원 id}`**
  - 예: `grn:team-4p8w2k9m1xza:vm-k3m9x2p7q4ta/snap-7qz3m8k2`
  - `/`는 GRN에도 id에도 나오지 않으므로, 첫 `/`에서 자르면 정확히 둘로 나뉜다
- **소유자는 따로 두지 않고 부모의 소유자를 쓴다.** 하위 자원 표는 부모 서비스 자원의 id를 가진다. 부모 id의 쓰임: 부모를 지우면 하위 자원도 지운다 / 하위 자원을 다루는 요청에서 실제 부모가 요청에 적힌 부모와 같은지 확인한다 / 부모를 기준으로 하위 자원 목록을 만든다
- **하위 자원의 인프라 부품(예: 포트포워딩 규칙)에는 그 하위 자원의 id를 적는다**
- **하위 자원은 한 단계만 둔다.** 하위 자원 밑에 또 하위 자원을 두지 않고, 하위 자원에 딸린 것은 부품이나 설정값으로 둔다. 예: 포트포워딩 규칙은 부품, 트리거의 cron 식은 트리거의 설정값
  - 이유: 표기가 `{부모 GRN}/{하위 id}` 한 가지로 끝나고 부모 확인도 한 번이면 된다. 두 단계를 허용하면 표기와 로더가 단계마다 늘어나고 부모 확인을 하나 빠뜨릴 여지가 생긴다
- **하위 자원 형식을 한 가지로 통일하는 이유**: 부모 안에서만 유일한 값(목록 순번, 이름)을 쓰면 식별이 (부모, 번호) 두 조각이 되어 소속 확인이 빠지기 쉽고, 순번은 앞 항목을 지울 때 바뀐다. 전역에서 유일한 id 하나로 가리키면 이런 실수가 구조적으로 줄어든다

## 6. 자원 모델과 층 규칙

### 세 층으로 나눈다

| 층 | 내용 | 관계 |
|---|---|---|
| 공통 자원(`Resource`) | 모든 서비스에 공통인 관리 정보. 서비스 자원만 들어간다 | |
| 서비스별 모델 | 서비스만의 값 | 자원 하나에 한 줄. 공통 자원과 같은 id (1:1) |
| 인프라 구현 층 | 실제 인프라 객체(부품) | 자원 하나에 여러 개일 수 있다 (1:N). 부품마다 자기가 속한 자원의 id를 적는다. 부품은 자원이 아니므로 GRN을 받지 않고, 사용자에게 보이지 않는다 |

- **공통 자원과 인프라 구현은 분리한다. 새 서비스를 추가해도 공통 자원은 고치지 않는다.** 공통 자원은 서비스끼리 연결하는 기준이라 항상 같은 모양을 유지해야 한다
- **공통 자원의 칸**: `id`, `name`, `type`, 소유자(개인 또는 팀), `status`, `tags`, `created_by`, `created_at`, `updated_at`
  - `project_id`는 두지 않는다. v2에는 프로젝트 개념이 없고 소유 주체는 개인 또는 팀이다
  - `region`은 두지 않는다. 위치를 사용자에게 숨기기로 했다
  - `name`: 사용자가 보는 이름이고 바꿀 수 있다. `id`는 이름과 독립적이고 바뀌지 않는다
  - `status`: 모든 서비스에 공통인 상위 상태를 두고, 필요하면 서비스별 상태를 따로 둔다
  - `tags`: 관리·분류용 메타데이터다. 자원의 동작을 정하지 않는다
  - `created_by`: 만든 사람. 팀 자원을 만든 사람이 팀을 나가도 기록은 남는다
  - 모델은 v2 서비스(VM, 서버리스 함수, 데이터베이스, 원터치 배포)만 만든다. 컨테이너·스토리지 같은 종류는 `type` 목록에 자리만 남기고 표를 미리 만들지 않는다

### 층 규칙 4가지

1. **모든 층을 unique resource id로 잇는다.** 서비스별 모델은 공통 자원과 같은 id를 쓴다. 인프라 부품은 자기가 속한 자원의 id를 적는다. 하위 자원은 부모 서비스 자원의 id를 가진다. 이유: 층끼리 서로를 찾는 방법을 id 하나로 통일하면 연결이 어긋나지 않는다
2. **값을 어느 층에 둘지는 질문을 순서대로 물어, 먼저 "예"가 나온 층에 둔다.**
   1. 모든 서비스에 공통이고, 서비스끼리 연결하는 데 필요한가? → 공통 자원
   2. 사용자가 정하거나 봐야 하는, 그 서비스만의 값인가? → 서비스별 모델
   3. Proxmox·Kubernetes 같은 기술을 바꾸면 사라지거나 바뀌는 값인가? → 인프라 구현 층 (사용자에게 안 보임)
   - 사용자에게 보이는 값은 사용자와의 약속이므로 서비스별 모델에 둔다. 구현 층에는 그 약속을 지키는 방법만 둔다. 구현을 바꿔도 사용자가 보는 값은 그대로여야 층을 나눈 의미가 있다
3. **GSMSV가 관리하는 기술용 이름·표시에는 바뀌지 않는 값(id, 소유자 id)만 쓴다.** 기술용 이름의 예: Proxmox VM 이름, Kubernetes 네임스페이스, 포트 규칙의 comment. 사용자가 지은 이름은 `name`에만 둔다. 예외: 만들 때 넘겨주고 GSMSV가 더 관리하지 않는 값(VM 안의 hostname 등)은 사용자 이름을 초깃값으로 써도 된다.
   - 이유: 사용자 이름을 인프라에 적으면 이름을 바꿀 때마다 인프라까지 고쳐야 하고, 안 고치면 틀린 정보가 남는다
   - 받아들인 불편: Proxmox 화면만 봐서는 누구 VM인지 모른다. 관리자 화면에서 id로 조회해서 해결한다
4. **id는 인프라를 만들기 전에 먼저 발급하고, 만드는 모든 인프라 객체에 적는다.** 공통 자원을 `creating` 상태로 먼저 저장해서 id를 확보한 다음 인프라를 만든다. 이유: "DB에 없는 id가 붙은 객체"(지워야 할 찌꺼기)와 "id가 없는 객체"(GSMSV 밖에서 만든 것)를 가를 수 있다. 모든 인프라 객체에 자원 id가 적혀 있어야, 지워진 자원의 객체가 남았는지 DB와 비교해 찾을 수 있다

## 7. 서비스별 목록 (하위 자원 / 설정값 / 부품 / 기록)

서비스 자원에 딸린 항목이 무엇인지는 **일반 기준으로 판정하지 않고, 서비스별 기능을 보고 직접 정해 아래 목록에 적는다. 목록에 적힌 것만 따른다.** 일반 기준을 적어 두면 나중에 그 기준이 들어맞지 않아야 할 경우에도 들어맞아 버릴 수 있다. 새 서비스나 기능을 설계할 때 그 항목들을 이 목록에 추가한다. (목록에 적는 것을 잊으면 판단할 근거가 없어진다)

**VM**

- 하위 자원: 스냅샷(`snap`, 직접 만든 것과 자동 스냅샷 모두), 포트포워딩(`port`), HTTPS 도메인 연결(`domain`), 방화벽 규칙(`fwrule`)
- 설정값: 사양(CPU·RAM·SSD), OS 이미지, 사용 목적, 사용 기간(만료일), 자동 스냅샷 켜기/끄기
- 부품: Proxmox VM, cloud-init 파일, 기본 포트 규칙(VM의 부품) / 포트포워딩 규칙(포트포워딩의 부품) / 프록시 라우트(HTTPS 도메인 연결의 부품) / Proxmox 스냅샷(스냅샷의 부품)
- 기록: VM 생성 작업, 알림, 감사 로그

**서버리스 함수**

- 하위 자원: 트리거(`trigger`, HTTP·예약), 버전(`version`), 도메인 연결(`domain`, VM과 같은 종류)
- 설정값: 함수는 코드, 런타임(JavaScript·TypeScript·Python), 환경변수(변수마다 비밀 표시), 실행 제한(메모리·시간), 활성 여부, 연결한 DB, 사용 기간 / 트리거는 HTTP면 받을 요청 방식과 호출 주소 토큰, 예약이면 cron 식
- 부품: 함수는 샌드박스 실행 환경, TypeScript 컴파일 결과, 환경변수·비밀 변수·DB 접속 정보를 담은 Kubernetes Secret, 네트워크 규칙, 임시 파일 공간 / 트리거는 호출 주소 라우팅 규칙(HTTP)과 스케줄 항목(예약) / 도메인 연결은 프록시 라우트와 인증서
- 기록: 실행 로그, 알림, 감사 로그(비밀 변수 변경, 호출 주소 재발급, 삭제)

**데이터베이스**

- 하위 자원: 백업(`backup`, 매일 자동 백업과 복원 직전 백업)
- 설정값: 엔진(MySQL·PostgreSQL), 격리 방식(공유형·전용형), 비밀번호(교체 가능), 사용 기간
- 부품: 공유형은 공유 DB 서버 안의 database와 그 database 전용 계정(둘 다 이름은 db id)과 권한 설정 / 전용형은 전용 DB 서버, 그 안의 관리자 계정, 소유자의 네임스페이스·VM에서만 닿게 하는 네트워크 규칙 / 백업 파일
- 기록: 발급 작업, 전용형 신청·승인·거절 기록, 알림, 감사 로그(비밀번호 조회·교체, 웹 쿼리 콘솔 실행 사실, 백업 내려받기·복원, 삭제)
- 개수·용량·연결 수 한도는 시스템 전체 설정값이라 목록에 넣지 않는다. 쓰기 금지와 정지는 상태로 다룬다

**원터치 배포 — 앱**

- 하위 자원: 서비스(`service`), 환경(`env`), 도메인 연결(`domain`), 배포 기록(`deployment`). "서비스 × 환경" 한 칸(실제로 도는 컨테이너)은 하위 자원이 아니라 설정값·부품으로 다룬다 (하위 자원 한 단계 규칙)
- 설정값: 앱은 이름, 사용 기간, PR 미리보기 설정 / 서비스는 종류(웹·워커·크론), 소스, 시작 명령, 공개 주소 여부, 상태 확인 경로, 배포 전 명령 / 환경은 연결한 브랜치, 자동 재배포, CI 대기 / 칸은 메모리·CPU, 환경변수, 연결한 DB, 상시 실행 여부, 서브도메인
- 부품: 실행 중인 컨테이너, 컨테이너 이미지, 빌드 캐시, Kubernetes 네임스페이스·NetworkPolicy·Secret, 공개 주소 라우팅 규칙, 내부 DNS 이름, GitHub 앱 설치와 웹훅 연결, 사용자 지정 도메인 인증서, 지표 수집 대상
- 기록: 배포 기록(빌드 로그 포함), 실행 로그, 승인 기록, 알림, 감사 로그(비밀 변수 변경, 승인·거절, 되돌리기, 저장소 연결 변경, 셸 접속, 삭제)

## 8. id 노출 원칙

- **원칙 ①: 안전을 id가 비밀이라는 데 기대지 않는다.**
  - id를 알아도 권한이 생기지 않도록, 모든 조회·조작은 자원 로더([22번](authorization.md))의 권한 확인을 거친다
  - id만 알면 쓸 수 있는 기능(공개 호출 주소, 공유 링크, 초대 링크 등)이 필요하면 id가 아니라 **별도 비밀 토큰**으로 막는다
  - 근거: AWS는 계정 ID·ARN을 비밀·민감 정보로 보지 않지만 조심해서 공유할 식별 정보로 본다. OWASP(IDOR 방지)는 추측하기 어려운 id는 보조 방어로 쓰고, 주 방어는 요청마다 하는 권한 확인이어야 한다고 한다
- **원칙 ②: id와 GRN은 아래 다섯 곳에서만 보여 준다. 나머지는 모두 안 된다 (허용 목록).**
  1. 그 자원을 볼 권한이 있는 사용자(본인·팀원)의 화면, API 응답, CLI 출력
  2. 관리자 화면
  3. 서버 로그, 감사 로그, 운영 리포트
  4. 인프라 객체의 태그·라벨·comment (층 규칙 4)
  5. 사용자가 보낸 id를 그 사용자에게 되돌려 주는 에러 메시지
  - 에러 메시지는 요청자가 보내지 않은 다른 자원의 존재나 id를 알려 주지 않는다. 사용자 문의는 공통 에러 형식의 `request_id`로 관리자가 로그에서 찾는다
  - 원칙 ②는 보조 방어이고 주 방어는 원칙 ①이다. 이미 id를 아는 사람(예: 팀에서 제외된 사람)은 ②로 막을 수 없고 ①이 막는다. ②에 기대는 설계를 하지 않는다
  - ②를 금지 목록이 아니라 허용 목록으로 한 이유: "필요 없는 곳"이라는 문구는 개발자마다 다르게 해석할 수 있다. 모호함 없이 쓰기 위해서다
- 로그·감사 로그·운영 리포트는 개발진만 볼 수 있다. 개발진에서 빠지는 사람은 그 접근도 함께 회수한다
- **받아들인 단점**: "알기만 하면 쓸 수 있는" 기능이 생길 때마다 토큰을 따로 설계해야 한다. ①은 ②와 반드시 한 쌍으로 적어야 한다("id는 아무 데나 써도 된다"로 오해하지 않게). 에러 메시지에 id가 없으므로 문의는 `request_id`로 찾아야 한다

## 9. HTTPS 도메인 연결의 인프라 부품

- 프록시 라우트의 식별값은 하위 자원 id(`domain-…`)를 쓴다. 사용자가 서브도메인을 바꿔도 식별값은 그대로이고, DB의 도메인 기록과 프록시 라우트가 id로 1:1로 이어져서 "DB에 없는 식별값"을 찌꺼기로 바로 찾을 수 있다 (층 규칙 3·4)
- **DB가 유일한 진실이다.** Go가 DB의 활성 도메인 목록으로 라우트 목록 전체를 만들어 프록시에 한 번에 교체한다
- 주기적으로 DB와 프록시 설정을 비교해, 어긋나면 DB 기준으로 되돌린다 (조정 루프)
- 단점(받아들임): 매번 전체를 교체하므로 라우트가 수만 개면 무거워진다. 교내 규모에서는 문제가 되지 않는다

## 10. 하면 안 되는 것

- GRN의 소유자 칸으로 권한을 판단하지 않는다
- GRN에 사용자가 정한 이름을 넣지 않는다. 서비스마다 GRN 모양을 달리하지 않는다
- GRN에 노드를 넣지 않는다. 사양, VM 번호, 만든 사람도 GRN이 아니라 모델에 둔다
- ULID처럼 생성 시각을 담거나 순서대로 커지는 방식으로 id를 만들지 않는다
- 사용자, 팀, 하위 자원에 GRN이나 공통 자원 행을 주지 않는다
- 하위 자원 밑에 또 하위 자원을 두지 않는다
- 하위 자원인지 부품인지를 일반 기준으로 판정하지 않는다. 서비스별 목록만 따른다
- 공통 자원에 `project_id`, `region` 칸을 두지 않는다. 컨테이너·스토리지 표를 미리 만들지 않는다
- 인프라 쪽 기술용 이름에 사용자가 정한 이름을 적지 않는다
- GRN 문자열을 직접 자르지 않는다. 파서만 쓴다
- 하위 자원 로더를 부모 GRN 없이 부르지 않는다
- 에러 메시지에 요청자가 보내지 않은 다른 자원의 id나 존재를 담지 않는다
- id만 알면 쓸 수 있는 공개 기능을 만들지 않는다. 필요하면 별도 비밀 토큰을 쓴다
- 지금 사용 중인 GRN과 같은 GRN은 만들 수 없다 (겹치면 서버가 다시 뽑는다)
