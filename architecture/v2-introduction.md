# GSMSV v2 소개 — 방향, V1과 달라지는 점, 사용자에게 제공할 것

> 이 문서는 프론트엔드·백엔드·DevOps(인프라) 개발자가 **GSMSV v2가 무엇을 만들려는 프로젝트인지** 처음 이해하기 위한 글이다. 규칙과 값은 이 문서에 다시 쓰지 않고 해당 문서로 연결한다. 규칙 문서와 이 문서가 다르면 규칙 문서가 맞다.
>
> 저장소가 공개되어 있어서 망 구성, 장비, 주소, 포트, 운영 절차는 쓰지 않는다. 그런 내용은 팀 내부 문서로 관리한다 ([구조 개요](overview.md) 9장).
>
> 표기: **확정**(정한 내용), **제안**(논의 중에 나온 안), **미정**(아직 정하지 않음, 담당을 함께 적는다). 따로 표시가 없으면 확정이다. 기능은 번호와 이름을 함께 쓴다. 예: 23번(자원 이름 규칙).

## 1. 이 문서를 읽는 법

### 1.1 읽고 나면 알게 되는 것

- v2가 어떤 방향으로 가는지, 왜 그 방향인지
- V1에서 무엇이 바뀌고 무엇이 이어지는지
- 사용자(학생·팀·관리자)가 v2에서 무엇을 할 수 있는지
- 내 역할(프론트엔드·백엔드·DevOps)이 어떤 문서부터 읽고, 무엇을 맡고, 무엇을 하면 안 되는지

### 1.2 이 문서가 하지 않는 것

- API 명세, 상수 값, 권한표 같은 **규칙 전체**를 옮겨 적지 않는다. 규칙이 두 곳에 있으면 한쪽이 낡아서 어긋난다
- 구현 방법을 정하지 않는다. 구현 세부는 담당이 개발하면서 정한다

### 1.3 역할별로 어디부터 읽는가

| 내 역할 | 먼저 읽을 곳 | 그다음 |
|---|---|---|
| 프론트엔드 (React) | 이 문서 4·5장 → [웹 API가 지킬 규칙](../rules/api-rules.md) | [자원 이름 규칙](../rules/resource-naming.md), [기능별 정책](../policies/feature-policies.md) |
| 백엔드 (Kotlin) | 이 문서 3·5장 → [팀·권한](../rules/team-ownership.md) → [권한 판단](../rules/authorization.md) | [웹 API가 지킬 규칙](../rules/api-rules.md), [Kotlin·Go 경계](../policies/kotlin-go-boundary.md) |
| DevOps·인프라 (Go) | 이 문서 3·6장 → [구조 개요](overview.md) 7장 | [Kotlin·Go 경계](../policies/kotlin-go-boundary.md), [할당량](../policies/quota.md), 서비스 문서 3개 |

세부 문서의 전체 읽는 순서는 [구조 개요](overview.md) 8장에 있다.

> **용어 주의**: 이 문서와 규칙 문서에서 「DevOps 엔지니어」는 **팀 안의 역할 이름**이다 (팀장·DevOps 엔지니어·일반 팀원, [팀·권한](../rules/team-ownership.md) 2.1). 이 문서를 읽는 DevOps 직군 개발자를 뜻하지 않는다. 직군은 "DevOps·인프라 개발자"라고 쓴다.

## 2. GSMSV는 무엇이고 누가 쓰는가

광주소프트웨어마이스터고 재학생이 쓰는 교내 인프라 플랫폼이다. 학생과 팀은 웹 콘솔에서 가상 머신(VM)을 신청해 쓰고, VM 대신 쓸 수 있는 서비스(서버리스 함수, 데이터베이스, 원터치 배포)를 발급받는다.

| 사용자 | 누구인가 | v2에서 얻는 것 |
|---|---|---|
| 일반 사용자 (USER) | 재학생 한 명 | 개인 VM과 개인 서비스 자원, 팀 참여 |
| 팀 | 같은 프로젝트를 하는 학생들이 만든 모임 | 팀이 소유하는 VM·서비스 자원을 팀원이 역할에 따라 함께 관리 |
| 관리자 (ADMIN) | 플랫폼을 운영하는 사람 | 팀 승인, 전체 자원 관리, 노드 현황 확인 |

팀 안의 역할은 팀장, DevOps 엔지니어, 일반 팀원 셋이다. 같은 사람이 팀마다 다른 역할을 가질 수 있다.

## 3. v2의 방향

### 3.1 한 문단 요약

**학생이 개인 VM 한 대에 모든 것을 설치해서 쓰는 방식에서, 필요한 서비스를 골라 발급받아 쓰는 방식으로 간다. 자원은 개인뿐 아니라 팀이 함께 소유하고, 한도는 VM 개수가 아니라 CPU·RAM·SSD 양으로 센다.**

### 3.2 핵심 원칙 다섯 가지

| 원칙 | 내용 | 왜 그런가 | 자세한 문서 |
|---|---|---|---|
| ① 서비스를 골라 쓴다 | VM 외에 서버리스 함수, 데이터베이스, 원터치 배포를 제공한다 | 개인 VM의 자원 한도는 크지 않다. 데이터베이스를 VM마다 직접 설치하면 그 자원을 학생이 그대로 써 버린다. 서비스로 제공하면 한도를 아끼면서 더 많은 것을 할 수 있다 | [서비스 4가지](overview.md) 3장 |
| ② 팀이 자원을 소유한다 | 자원의 소유자는 개인 또는 팀 하나다 | 같은 프로젝트를 하는 학생들이 한 VM을 함께 봐야 한다. 한 사람만 소유하면 다른 팀원은 볼 수도, 관리할 수도 없다 | [팀·권한](../rules/team-ownership.md) |
| ③ 권한 판단은 한 곳에서 한다 | 모든 요청을 "누가, 무엇을, 어느 자원에"로 한 관문에서 판단한다. 기본값은 거부다. 관리자도 같은 관문을 지난다 | 판단 코드가 곳곳에 흩어지면 하나만 빠뜨려도 다른 사람의 자원이 열린다 | [권한 판단](../rules/authorization.md) |
| ④ 자원을 양으로 센다 | 한도는 개수가 아니라 CPU·RAM·SSD 할당량이다 | 개수로 세면 사양이 작아도 한 대, 최대 사양이어도 한 대로 센다. 실제 자원 소모와 한도가 맞지 않는다 | [할당량](../policies/quota.md) |
| ⑤ 계약을 먼저 정한다 | API를 새로 만들거나 바꿀 때는 구현보다 이 저장소의 명세 PR을 먼저 올린다 | 프론트엔드·백엔드가 서로 다른 API를 상상한 채 개발하는 일을 막는다 | [웹 API가 지킬 규칙](../rules/api-rules.md) |

### 3.3 런칭 범위와 일정

| 구분 | 범위 | 일정 |
|---|---|---|
| 1차 런칭 | V1의 기능 전부 + 원터치 배포(25번) + 데이터베이스 발급(24번, DBaaS) | 2026년 12월 14일(월). 전환은 12월 12일(토)~13일(일) 주말에 하고, 월요일부터 v2를 쓴다 |
| 2차 런칭 | 서버리스(15·16·17번)와 서비스의 2차 항목 | 2026년 말, 12월 25일(크리스마스) 이후. 정확한 날은 **미정** |

- 위 범위와 날짜는 사용자(기획 담당)가 정했다. 날짜가 바뀌면 이 표를 고친다
- 서비스를 1차와 2차로 나눈 항목의 세부는 서비스 문서에 있다
- **이 일정 정보가 바뀌었는데 이 표를 고치지 않으면 읽는 사람이 잘못된 날짜를 믿는다.** 날짜를 다른 문서에 복사하지 말고 이 표를 가리킨다

## 4. 사용자에게 제공할 것

사용자 시점에서 v2가 주는 기능이다. 각 기능의 규칙은 오른쪽 문서가 원본이다.

### 4.1 가상 머신 (V1에서 이어지는 핵심 기능)

| 사용자가 할 수 있는 일 | 확정한 규칙 요약 | 원본 |
|---|---|---|
| VM 신청 | 개인 VM과 팀 VM 생성 화면을 따로 둔다. 진행 상태를 단계(대기 → 복제 → 설정 → 부팅 → 네트워크 등록 → 완료)로 보여 준다 | [기능별 정책](../policies/feature-policies.md) 5번 |
| 사양 고르기 | 티어 대신 슬라이더로 vCPU·RAM·SSD를 직접 고른다. 운영체제는 Ubuntu 22.04 LTS·24.04 LTS, Debian 13 | [할당량](../policies/quota.md) 5장 |
| VM 관리 | 전원 제어, 사양 변경(디스크는 늘리기만), 스냅샷, 포트포워딩, 방화벽, HTTPS 도메인 연결 | [팀·권한](../rules/team-ownership.md) 2.2 |
| 사용 기간 | 개인 VM은 14일, 연장은 만료 7일 전부터 14일씩. 연장하지 않으면 정지 → 3일 유예 → 삭제 | [기능별 정책](../policies/feature-policies.md) 8번 |
| 알림 | 만료·삭제 같은 필수 알림은 학교 이메일로도 보낸다. Discord 연결은 선택이다 | [기능별 정책](../policies/feature-policies.md) 19번 |
| 가이드 문서 | 웹 콘솔의 `/docs`에 사용자 가이드를 둔다 | [기능별 정책](../policies/feature-policies.md) 32번 |

### 4.2 서비스 세 가지 (v2의 새 방향)

| 서비스 | 사용자가 하는 일 | 무엇을 대신해 주는가 | 원본 |
|---|---|---|---|
| 데이터베이스 (24번) | 웹 콘솔에서 MySQL·PostgreSQL을 발급받는다 | VM 안에 DB를 직접 설치하고 백업하는 일. 매일 백업과 웹 쿼리 콘솔을 제공한다 | [데이터베이스](../services/database.md) |
| 원터치 배포 (25번) | GitHub 저장소를 연결한다 | 코드 빌드, 실행, 공개 주소와 HTTPS 연결. push하면 자동 재배포한다 | [원터치 배포](../services/one-touch-deploy.md) |
| 서버리스 (15·16·17번) | 코드 조각(함수)만 올린다 | 요청이나 정해진 시각에 실행하고, 실행 기록을 보여 준다. 2차 런칭이다 | [서버리스](../services/serverless.md) |

- 세 서비스의 역할 구분: 짧게 끝나는 코드는 **서버리스**, 계속 떠 있어야 하는 웹 앱은 **원터치 배포**, 데이터 저장은 **데이터베이스**, root 권한이 필요한 작업은 **VM**이다
- 서비스 자원의 개수·용량은 VM 한도와 따로 센다. 서비스를 써도 VM 한도가 줄어들면 VM 대신 서비스를 쓸 이유가 없기 때문이다 ([할당량](../policies/quota.md) 2장)

### 4.3 팀과 계정

| 기능 | 내용 | 원본 |
|---|---|---|
| 팀 만들기 | 팀을 만들고 관리자가 승인하면 팀 할당량이 생긴다. 만든 사람이 팀장이다. 승인 대기 중인 팀은 VM을 만들 수 없다 | [팀·권한](../rules/team-ownership.md) |
| 팀원 관리 | 팀장이 초대·제외하고 DevOps 역할을 부여한다 | [팀·권한](../rules/team-ownership.md) 2.2 |
| 로그인 | 한 사람은 계정 하나다. 역할 토글은 없다. 졸업이 반영되면 일반 사용자는 쓸 수 없다 | [기능별 정책](../policies/feature-policies.md) 1번 |

### 4.4 사용자가 알아 둘 한계 (의도한 결정)

- GSMSV 권한은 **콘솔과 API의 동작만** 막는다. VM 안에서 하는 일은 막지 않는다 ([팀·권한](../rules/team-ownership.md) 2.3)
- 팀에서 일반 팀원은 코드나 설정을 고칠 수 없다. 함께 개발하려면 팀장이 DevOps 역할을 준다

## 5. V1과 달라지는 점

V1의 운영 방식은 이어서 쓸 수 있는 부분이 많다. 아래는 **바뀌는 것**만 적었다. 바꾼 이유는 v2의 방향 기준으로 적었다.

| 항목 | V1 | V2 | 바꾸는 이유 |
|---|---|---|---|
| 계정과 소유 | 일반 사용자와 프로젝트 오너가 별도 계정 종류. 자원은 계정 하나가 소유 | 계정 종류는 USER·ADMIN 둘뿐. 자원은 개인 또는 팀이 소유하고, 팀 안에서 역할을 나눈다 | 같은 프로젝트를 하는 사람들이 한 자원을 함께 관리해야 한다 |
| 한도 | VM 개수와 티어(BASIC·STANDARD·ADVANCED·PROJECT_CUSTOM) 중심 | CPU·RAM·SSD 할당량. 사양은 슬라이더로 직접 고른다 | 자원을 실제로 쓰는 양과 한도를 맞추고, 사용자가 필요한 사양을 정확히 고르게 한다 |
| 제공하는 것 | VM 신청·관리, 서버리스 | VM, 서버리스, 데이터베이스, 원터치 배포 | 개인 VM 한도 안에서 더 많은 것을 하게 한다 (3.2 ①) |
| 서버리스 | 이미 있는 구현 | **처음부터 다시 만든다.** 2차 런칭 | 새 소유·권한·이름 규칙과 서비스 구조에 맞춰 설계한다 |
| 기술 스택 | 백엔드 FastAPI(Python), 프론트엔드 Next.js, 서버리스 Node | API 서버 Kotlin, 인프라 실행 엔진 Go, 웹 콘솔 React | 인프라 작업은 인프라를 아는 사람이 자기 언어로 쓰고, 나머지 API 서버는 Kotlin이 맡는다 ([Kotlin·Go 경계](../policies/kotlin-go-boundary.md) 1장) |
| 저장소 | 백엔드·서버리스를 한 저장소에 두고 프론트엔드는 따로 둠 | Server·Client·Infra·Contracts 네 곳으로 나눈다 | 역할마다 맡는 곳을 나누고, 공통 약속은 Contracts 한 곳에 둔다 |
| 개발 방식 | 구현하면서 API를 정한다 | 명세를 먼저 쓰고 구현한다 (계약 먼저) | 3.2 ⑤ |
| 자원 식별 | 자원 종류마다 방식이 다르다 | 모든 서비스 자원을 GRN `grn:{소유자 id}:{자원 id}` 하나로 가리킨다 | 소유와 권한 판단을 한 방식으로 통일한다 ([자원 이름 규칙](../rules/resource-naming.md)) |

**V1에서 이어지는 것**: VM 신청과 관리, 사용 기간(만료·연장), 스냅샷, 방화벽·포트포워딩, 알림, 관리자 승인, 가이드 문서. 기능명세서에서 「V1 기존」「V2 변경」으로 분류된 항목이다. 이어 가는 항목도 위의 소유·한도·이름 규칙을 따른다.

## 6. 구성과 요청 흐름

| 저장소 | 역할 | 언어 |
|---|---|---|
| `GSMSV-Client-V2` | 웹 콘솔 | React |
| `GSMSV-Server-V2` | API 서버: 데이터의 진실, 권한 판단, 할당량, 정책 | Kotlin |
| `GSMSV-Infra-V2` | 실행 엔진: Proxmox·Kubernetes를 직접 다룬다 | Go |
| `GSMSV-Contracts-V2` (이 저장소) | 저장소끼리 함께 쓰는 약속 | 문서·명세 |

```text
브라우저(Client) → API 서버(Server) → 실행 엔진(Infra) → Proxmox / Kubernetes
```

- 권한 판단은 API 서버에서만 한다. 실행 엔진에는 권한 판단 코드를 두지 않는다
- 실행 엔진은 내부에서만 닿는다. 브라우저가 직접 붙지 않는다
- VM은 Proxmox에 두고, 서비스는 Kubernetes 위에 둔다. 학생 코드는 데이터와 같은 노드에서 돌리지 않는다
- 자세한 인프라 원칙: [구조 개요](overview.md) 7장

## 7. 역할별로 맡는 것과 하면 안 되는 것

### 7.1 프론트엔드 (React)

- **맡는 일**: 웹 콘솔 화면. API 명세에 맞춘 호출, 생성 진행 표시(SSE), 사용자 가이드 화면
- **먼저 알아야 할 것**: 자원을 GRN으로 가리킨다. 사용자가 정한 이름은 `name`이고 바꿀 수 있다. GRN에는 들어가지 않는다
- **하면 안 되는 것**
  - 버튼을 숨기는 것으로 권한을 대신하지 않는다. 숨기기는 편의이고, 막는 일은 서버가 한다
  - 노드 정보와 VM 번호 같은 구현 값을 화면에 보이지 않는다. 노드 정보는 관리자 화면에서만 보인다
  - GRN의 소유자 칸을 읽어 화면의 권한을 판단하지 않는다
- **아직 정해지지 않은 것(미정)**: URL에 GRN을 넣는 방법, `permissions` 키 형식, 공통 에러 `code` 목록, 목록 페이지 나누기. 백엔드와 함께 API 명세 PR에서 정한다 ([웹 API가 지킬 규칙](../rules/api-rules.md) 3장)

### 7.2 백엔드 (Kotlin)

- **맡는 일**: 데이터(DB), 권한 판단, 할당량 계산, 어디에 얼마를 줄지의 정책, 사용자에게 보일 문구
- **먼저 알아야 할 것**: 권한은 DB에 저장된 소유자로만 판단한다. 자원 로더 한 곳에서 판단하고, 목록은 같은 규칙을 쓰는 짝 함수로 처리한다
- **하면 안 되는 것**
  - 권한 판단을 실행 엔진(Go)으로 넘기지 않는다
  - 볼 수 없는 자원을 403으로 답하지 않는다. 볼 수 없으면 404, 볼 수는 있지만 권한이 없으면 403이다
  - 응답에 노드·VM 번호 같은 구현 값을 넣지 않는다
  - 부모 GRN 없이 하위 자원 id만으로 찾는 API를 만들지 않는다
- **아직 정해지지 않은 것(미정)**: 팀 이름 규칙, 초대 같은 팀 쪽 항목의 형식, 동작 이름과 `permissions`, 감사 로그, Server ↔ Infra 사이 형식 ([권한 판단](../rules/authorization.md) 9장, [Kotlin·Go 경계](../policies/kotlin-go-boundary.md))

### 7.3 DevOps·인프라 (Go)

- **맡는 일**: Proxmox와 Kubernetes를 다루는 실행 엔진. 오래 걸리고 동시에 많이 일어나는 작업(VM 생성, 서비스 프로비저닝), 상태 모으기
- **먼저 알아야 할 것**: 경계는 "무엇을 하느냐"가 아니라 **얼마나 오래, 얼마나 많이 동시에 일어나느냐**로 자른다. 대부분 **제안** 단계이며 팀이 확정한다 ([Kotlin·Go 경계](../policies/kotlin-go-boundary.md) 2장)
- **하면 안 되는 것**
  - 권한 판단 코드를 두지 않는다
  - 브라우저에 직접 닿는 경로를 만들지 않는다
  - 망 구성, 주소, 포트, 도메인을 이 저장소에 쓰지 않는다. 팀 내부 문서로 공유한다
- **아직 정해지지 않은 것(미정)**: 서비스 몫(서버리스·데이터베이스·원터치 배포가 쓰는 자원)의 크기, 서비스 실행 환경의 구성, Server ↔ Infra 사이 형식(REST + OpenAPI 또는 gRPC)

## 8. 이 저장소에서 아직 정하지 않은 것

| 항목 | 정하는 담당 |
|---|---|
| 폴더 구조와 상수 파일 형식 | 각 저장소 담당 (이 구조는 제안이다) |
| 다른 저장소로 계약을 전달하는 방법, 버전 태그, 깨지는 변경의 처리 | 백엔드·프론트엔드·DevOps 합의 |
| `develop`에서 API 변경을 승인하는 규칙 | 팀 합의 |
| 서비스 몫의 크기, 운영·관리자 몫의 크기 | 기획 (서비스 설계와 출시 직전 실측 뒤) |

## 9. 용어

| 용어 | 뜻 |
|---|---|
| GSMSV | 광주소프트웨어마이스터고 교내 인프라 플랫폼 |
| VM(인스턴스) | 학생이 신청하는 가상 머신. 자원 id가 `vm-`로 시작한다 |
| 서비스 자원 | VM·함수(`fn-`)·데이터베이스(`db-`)·앱(`app-`)처럼 GSMSV가 발급하고 세는 자원 |
| GRN | 자원의 이름. `grn:{소유자 id}:{자원 id}` 형식 ([자원 이름 규칙](../rules/resource-naming.md)) |
| 팀장 / DevOps 엔지니어 / 일반 팀원 | 팀 안의 역할. 직군이 아니라 권한 단위다 (1.3 용어 주의) |
| 할당량 | 사양을 합한 값(CPU·RAM·SSD). 실제 사용량이 아니다. 꺼진 VM도 센다 |
| 계약 먼저 | 구현보다 명세 PR을 먼저 올리는 개발 방식 |
| 자원 로더 | 자원을 읽으면서 권한도 함께 판단하는 한 곳의 코드 ([권한 판단](../rules/authorization.md)) |
| 샌드박스 | 학생이 올린 코드를 가둬서 실행하는 격리된 컨테이너 |
