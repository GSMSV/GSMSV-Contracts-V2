# GSMSV v2 구조 개요

> 이 문서는 GSMSV v2의 **전체 구조를 이해하기 위한 입구**다. 저장소가 공개되어 있어서 망 구성, 장비, 주소, 포트, 운영 절차는 이 저장소에 쓰지 않는다. 그런 내용은 비공개 문서에서 관리한다.

## 표기

| 표기 | 뜻 |
|---|---|
| **확정** | 정한 내용이다. 바꾸려면 논의가 필요하다 |
| **제안** | 논의 중에 나온 안이다. 확정이 아니다 |
| **미정** | 아직 정하지 않았다. 정하는 담당을 함께 적는다 |

기능은 번호만 쓰지 않고 이름을 함께 적는다. 예: 23번(자원 이름 규칙).

## 1. GSMSV는 무엇인가

광주소프트웨어마이스터고 재학생이 쓰는 교내 인프라 플랫폼이다. 학생과 팀은 웹 콘솔에서 VM을 신청해 쓰고, VM 대신 쓸 수 있는 서비스(서버리스 함수, 데이터베이스, 원터치 배포)를 발급받는다.

## 2. 구성 요소

| 저장소 | 역할 | 언어 |
|---|---|---|
| `GSMSV-Client-V2` | 웹 콘솔 (사용자가 보는 화면) | React |
| `GSMSV-Server-V2` | API 서버. 데이터(DB)의 진실, 권한 판단, 할당량, 어디에 얼마를 줄지의 정책, 사용자에게 보일 문구 | Kotlin |
| `GSMSV-Infra-V2` | 인프라 실행 엔진. Proxmox와 Kubernetes를 직접 다룬다. 오래 걸리고 동시에 많이 일어나는 작업을 맡는다 | Go |
| `GSMSV-Contracts-V2` (이 저장소) | 저장소끼리 함께 쓰는 약속: API 명세, 자원 식별자 상수, 공통 규칙 | 문서·명세 |

요청이 지나가는 길은 다음과 같다.

```text
브라우저(Client) → API 서버(Server) → 실행 엔진(Infra) → Proxmox / Kubernetes
```

- 권한 판단은 API 서버에서만 한다. 실행 엔진에는 권한 판단 코드를 두지 않는다
- 실행 엔진은 내부에서만 닿는다. 브라우저가 직접 붙지 않는다
- 두 서버 사이의 책임 나눔은 [Kotlin·Go 경계](../policies/kotlin-go-boundary.md)에 있다

## 3. 서비스 네 가지

| 서비스 | 자원 id | 무엇인가 | 실행되는 곳 |
|---|---|---|---|
| VM (인스턴스) | `vm-…` | 학생이 신청하는 가상 머신 | Proxmox |
| 서버리스 함수 | `fn-…` | 코드 조각만 올리면 요청이나 정해진 시각에 실행해 주는 서비스 | Kubernetes 위 샌드박스 |
| 데이터베이스 | `db-…` | MySQL·PostgreSQL을 발급받아 쓰는 서비스 | Kubernetes |
| 원터치 배포 (앱) | `app-…` | GitHub 저장소를 연결하면 빌드해서 띄우고 주소까지 붙여 주는 서비스 | Kubernetes 위 샌드박스 |

- 방향: 학생이 개인 VM만으로 모든 것을 하지 않고, 필요한 만큼 서비스를 쓰게 한다. 개인 VM의 자원 한도는 크지 않다
- 서비스별 기획: [데이터베이스](../services/database.md) · [서버리스](../services/serverless.md) · [원터치 배포](../services/one-touch-deploy.md)

## 4. 소유와 권한

- 자원의 소유자는 **개인 또는 팀** 하나다. 여러 팀이 함께 소유하지 않고, 개인 자원을 팀 자원으로 바꾸지 않는다
- 전역 역할은 일반 사용자(USER)와 관리자(ADMIN) 둘이다. 팀 안의 역할은 팀장, DevOps 엔지니어, 일반 팀원 셋이다
- 모든 요청은 "누가, 무엇을, 어느 자원에" 세 가지로 한 곳에서 판단한다. 기본값은 거부다. 관리자도 같은 관문을 지난다
- 볼 수 없는 자원은 404, 볼 수는 있지만 권한이 없는 동작은 403으로 응답한다
- 자세한 규칙: [팀·권한](../rules/team-ownership.md) · [권한 판단](../rules/authorization.md)

## 5. 자원 이름 (GRN)

- 서비스 자원은 `grn:{소유자 id}:{자원 id}`로 가리킨다. 하위 자원은 `{부모 GRN}/{하위 자원 id}`다
- id는 접두사와 무작위 문자열이다. 사용자가 정한 이름은 id와 따로 있고 바꿀 수 있다
- 권한은 GRN 안의 소유자 칸이 아니라 DB에 저장된 소유자로 판단한다
- 자세한 규칙: [자원 이름 규칙](../rules/resource-naming.md) · [상수 값](../constants/resource-id.md)

## 6. 자원 한도

- VM 개수가 아니라 CPU·RAM·SSD 할당량으로 센다
- 일반 사용자 1인 한도와 팀 한도는 고정된 설정값이다. 서비스(DB 개수·용량, 함수·앱 개수)는 VM 한도와 따로 센다
- 자세한 규칙: [할당량](../policies/quota.md)

## 7. 인프라 원칙

구체적인 구성, 장비, 주소, 허용 목록은 비공개 문서에 있고 이 저장소에 쓰지 않는다. 아래는 구조를 이해하는 데 필요한 **확정 원칙**이다.

1. 안쪽 망은 용도별로 나누고, 나뉜 곳 사이의 통신은 기본으로 막은 뒤 필요한 것만 연다
2. 노드는 사용자에게 보이지 않는다. 시스템이 자원이 많이 남은 곳에 자동으로 배분하고, 노드 정보는 관리자 화면에서만 보인다
3. VM은 Proxmox에 둔다. 서비스(서버리스·데이터베이스·원터치 배포)는 Kubernetes 위에 둔다. Kubernetes는 kubeadm으로 직접 설치하고, 노드는 Proxmox 위의 VM이다
4. 서버리스·데이터베이스·원터치 배포는 서로 칸을 나누고, 기본은 막고 필요한 것만 연다
5. 학생 코드는 데이터와 같은 노드에서 돌리지 않는다. GSMSV 본체(API 서버·웹 콘솔)는 학생 코드와 같은 클러스터에 올리지 않는다
6. 학생이 올린 코드(서버리스 함수, 앱)는 강한 격리를 가진 샌드박스 컨테이너에서 돌린다. 바깥으로 나가는 통신은 웹 포트만 열고, 사설 대역과 학생 VM으로는 나가지 못하게 막는다
7. 서비스에서 데이터베이스로 가는 길은 DB 포트만 연다. 소유자마다 최소 권한 계정을 쓰고, TLS를 필수로 하며, 비밀번호는 코드에 적지 않고 GSMSV가 Secret으로 넣어 준다

## 9. 이 저장소에 쓰지 않는 것

- 망의 구성, 장비, 주소, 포트, 도메인 구조
- 운영 절차, 계정, 비밀값, 서버 상태
- 용량과 사용자 수 같은 규모 정보

이런 내용은 팀 내부 문서로 공유한다. 이 저장소의 문서에서 이런 값을 발견하면 PR을 올리거나, 보안 문제라면 저장소 **Security** 탭으로 비공개 신고한다.
