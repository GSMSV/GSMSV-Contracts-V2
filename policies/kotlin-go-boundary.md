# 34번(Kotlin과 Go의 역할을 나눈다) — API 서버와 실행 엔진의 경계

> 상태: **방향은 합의**했다. Go가 인프라(Proxmox·Kubernetes)를 맡고, API 서버(Kotlin)와의 경계는 각 언어의 특성이 드러나게 나눈다. 그 밖의 세부는 모두 **제안**이며 팀과 확정한다. 이 문서는 개발을 시작하는 데 지장이 없는 수준의 방향을 적은 것이고, 세부는 개발하면서 팀이 정한다.
>
> 함께 읽을 문서: [22번(권한 판단)](../rules/authorization.md) · [23번(자원 이름 규칙)](../rules/resource-naming.md) · [구조 개요](../architecture/overview.md)
>
> 표기: **확정**, **제안**, **미정**. 이 문서에서 "제안"이라고 적지 않은 부분은 1장의 전제와 4장의 경계 원칙(확정된 방향)이다.

## 1. 전제

- **스택(확정)**: API 서버는 Kotlin, Proxmox·Kubernetes 연동은 Go, 프론트엔드는 React다
- Proxmox API는 HTTPS REST라 언어 제한이 없다. **Go를 쓰는 이유는 "Go만 된다"가 아니라 ① 인프라를 아는 사람이 자기 언어로 인프라 코드를 쓰고 ② Go의 동시성 모델이 느린 하이퍼바이저 작업에 맞기 때문이다**
- 권한 판단은 Kotlin에서만 한다 ([22번](../rules/authorization.md))

## 2. 경계를 자르는 기준: 수명과 동시성

"무엇을 하느냐(도메인)"로만 자르면 어떤 언어로 짜도 똑같은 구조가 나온다. Go를 고른 이유(빠르고, 병렬로 실행하고, 오래 걸리는 VM 생성을 보완해 빠른 서비스를 운영)가 드러나지 않는다. 그래서 **얼마나 오래, 얼마나 많이 동시에 일어나는가**로 자른다.

| 모델 | 경계 기준 | Go의 역할 |
|---|---|---|
| 1. 작업 단위 | 의미 있는 한 덩어리 | 요청받아 실행하고 끝. 상태 없음 |
| **2. 실행 엔진 (제안)** | 얼마나 오래, 얼마나 많이 동시에 | 동시성 제어, 진행률, 취소, 연결 유지, 상태 캐시를 소유 |
| 3. 조정 루프 | 원하는 상태 vs 실제 상태 | Kotlin이 원하는 상태를 쓰면 Go가 계속 맞춘다 |

**제안**: 모델 2를 기본으로 하고, 설정성 자원(포트 규칙, HTTPS 라우트, Kubernetes 테넌트)과 워밍 풀에만 모델 3을 섞는다.

## 3. 근거 사실

| 사실 | 설계에 주는 영향 |
|---|---|
| Proxmox는 클론을 직렬화한다. 클론 중 잠금이 걸리고, 다른 클론은 최대 60초 기다린 뒤 잠금 시간 초과로 실패한다 | "VM 여러 대를 동시에 클론"은 언어와 무관하게 실패한다. 노드·스토리지별로 줄을 세워야 한다 |
| 씬 프로비저닝 스토리지는 링크드 클론(복사-쓰기)을 지원한다 | 클론 시간을 가장 크게 줄일 수 있는 수단이다 |
| Proxmox는 상태를 약 10초마다 모으고, API는 그 모아 둔 값을 돌려준다 | 10초보다 자주 물어도 같은 값을 받는다 |
| 클론은 같은 노드 안에서만 한다 | OS 템플릿이 모든 노드에 있어야 한다 |
| cloud-init 설정을 바꾸면 다음 부팅에 초기화가 다시 돈다 (SSH 호스트 키 재생성 등) | 워밍 풀 VM은 한 번도 부팅하지 않은 상태로 둬야 한다 |
| 사양 변경 때 그 노드에 자리가 없으면 거절한다 | 노드 선택은 Kotlin이 하고, 판단 재료는 Go가 즉시 준다 |

## 4. 경계표

| | Kotlin | Go |
|---|---|---|
| 성격 | 짧고 트랜잭션적, 사람을 향함 | 길고 동시적, 기계를 향함 |
| 시간 단위 | 밀리초 | 초·분, 그리고 상시 |
| 소유 | DB(진실), 권한·할당량·비율 정책, 노드 **선택**, VM 번호·IP·포트 유일성, 사용자에게 보일 문구, 스케줄 트리거 | 실행 동시성, 노드별 클론 직렬 게이트, 진행률, 취소, 연결·세션, 상태 캐시, 조정 루프, 워밍 풀 |
| 판단 | 누구에게 얼마를 줄지 (자원 배분 정책) | 지금 몇 개를 어떤 순서로 돌릴지 (실행 동시성 정책) |

- **"무엇을·어디에"는 Kotlin, "어떻게"는 Go**다
  - Kotlin이 정해서 넘기는 것: 노드, VM 번호, 내부 주소, 사양, 이름, cloud-init 값, 만료일, 소유자
  - Go가 알아서 하는 것: Proxmox 호출 순서, 작업 상태 확인 간격·타임아웃, 재시도, 부분 생성 뒷정리, 연결 관리
- 노드 선택은 Kotlin이 하되, 판단 재료(노드 여유 + **현재 클론 대기 줄 길이**)는 Go가 캐시에서 즉시 준다
- VM 번호 선택은 다른 규칙(포트 계산, DB)을 봐야 하므로 Kotlin이 후보를 넘기고, Proxmox에서 이미 쓰이면 Go가 "번호 충돌" 코드를 돌려주고, Kotlin이 다음 후보로 다시 시도한다

### 레드라인 — Go에 넣지 않는 것

할당량 계산 / 노드 선택 / 권한 판단 / 만료 정책 / 팀·사용자 개념 / DB 접근 / 사용자에게 보일 문장

이 중 하나라도 Go로 들어가려 하면 경계가 무너지는 신호다. Go 서비스 엔드포인트가 열 개를 크게 넘어도 경계가 흐려지는 신호로 본다.

## 5. Go 실행 엔진이 줄이려는 시간 (제안)

| 구간 | 설계 | 쓰는 Go 기능 |
|---|---|---|
| 생성 전 노드 자원 조회 | TTL 캐시 (7.4) | `sync.RWMutex` |
| 클론 | 노드·스토리지별 직렬 게이트로 잠금 충돌 자체를 없앤다. 링크드 클론 검토 | 세마포어 채널 |
| 클론 대기 중 | 포트 예약·라우트 준비·DB 보고를 겹쳐 처리 (7.3) | `errgroup` |
| 규칙 등록 | 원격 연결을 유지하고 매번 새로 연결하지 않는다 | 연결 재사용 |
| 사용자 화면 | 단계별 진행률 (7.5) | 채널 fan-out |
| 취소 | 취소하면 전 구간 즉시 중단·정리 | `context` |
| 일일 스냅샷 | 동시 N개 제한으로 병렬 | `errgroup.SetLimit` |
| 남은 규칙 | 주기적인 조정 루프가 원하는 상태로 되돌린다 | goroutine + ticker |

**정직하게**: Go라서 코드가 빨라져 생성이 짧아지는 것이 아니다. 단축은 링크드 클론, 워밍 풀, 단계 겹치기, 캐시에서 온다. Go의 기여는 이 설계를 **기본 경로**로 만들어 준다는 것이다.
- 표준 라이브러리 I/O가 전부 고루틴 친화적이라, 동기 라이브러리가 이벤트 루프를 막는 문제가 구조적으로 없다
- `context`로 취소·데드라인을 전파하는 게 관례라 정리 로직이 새지 않는다
- Kubernetes를 다룰 때 client-go 생태계가 기본이다
- Kotlin도 코루틴으로 동시성은 된다. 차이는 위 세 가지와 담당자다

## 6. 계약 설계 (제안)

### 6.1 오래 걸리는 작업

- Go가 작업 id를 즉시 돌려주고 Kotlin이 폴링한다. 동기로 끝까지 기다리면 HTTP 타임아웃·재시작에 취약하고, 콜백은 호출 방향이 하나 늘고 재시도가 복잡하다
- **진실은 Kotlin DB에 둔다.** Go의 작업 상태는 휘발성으로 보고, Go가 재시작해 작업을 잃으면 Kotlin이 Proxmox 실제 상태를 조회해 복구한다

### 6.2 멱등성

- 호출이 중간에 끊기면 Kotlin은 작업이 됐는지 모른다. 작업마다 고유 키(요청 id)를 보내고, Go는 같은 키를 두 번 실행하지 않는다

### 6.3 선언형 vs 명령형

- **설정성 자원은 선언형**: 포트 규칙, HTTPS 라우트, Kubernetes 테넌트. "이 VM의 포트 집합은 이게 전부다"를 통째로 주면 Go가 현재 상태와 차이만 적용한다. 삭제된 자원의 규칙이 남는 문제는 선언형으로 원하는 상태를 주기적으로 다시 보내면 잔존 규칙이 사라진다
- **행위는 명령형 + 멱등 키**: VM 생성·삭제·전원·스냅샷

### 6.4 에러 계약

- Go는 사용자에게 보일 문장을 만들지 않는다. 기계가 읽는 코드와 원인 데이터만 돌려준다

  ```json
  {"code":"<에러 코드>","detail":{"<원인 데이터>":"<값>"},"request_id":"<요청 id>"}
  ```

- **재시도 가능한 실패**(Proxmox 타임아웃, 연결 끊김)와 **불가능한 실패**(사양 초과, VM 번호 충돌, 템플릿 없음)를 구분해 표시한다
- 사용자 문구는 Kotlin이 만든다. 내부 예외 원문이 사용자에게 노출되지 않는다. [22번](../rules/authorization.md)의 공통 에러 형식과 이어진다

### 6.5 인증·배치·자격증명

- Go 실행 엔진은 브라우저가 직접 붙지 않는 내부 서비스다
- 서비스 사이 인증과 자격증명 관리 방식은 비공개 문서에서 정한다. 이 저장소에는 쓰지 않는다

### 6.6 계약 정의와 개발 편의

- REST + OpenAPI로 스키마를 정의하고 양쪽 코드를 생성하는 것을 **제안**한다. 내부 호출량이 적고 팀이 REST에 익숙하다. gRPC는 타입 안정성·스트리밍이 좋지만 지금은 학습 비용이 더 크다 (미정, 6.8)
- Go에 **가짜 모드**를 둬서 Proxmox 없이도 뜨게 한다. Kotlin 개발자가 인프라 없이 개발할 수 있고 테스트 환경 부담도 준다

### 6.7 엔드포인트의 형태

- 엔드포인트 목록은 개발하면서 정한다. 이 저장소의 OpenAPI로 계약을 올리기 전에는 확정하지 않는다
- 자원은 [23번](../rules/resource-naming.md)에 따라 unique resource id로 가리킨다
- 형태는 6.3의 구분을 따른다: VM 생성·삭제·전원·사양·스냅샷은 비동기 명령형, 포트·HTTPS 라우트·Kubernetes 테넌트는 선언형, 노드 여유와 지표는 조회다

### 6.8 경계를 검증하는 방법

"VM 한 대 생성"을 React → Kotlin(권한 → 할당량 → 노드 선택) → Go(`POST /vms`) → 폴링 → 완료까지 한 줄기로 먼저 관통시킨다. 계약, 인증, 에러 코드, 멱등 키, 로그 상관관계가 여기서 한 번씩 다 쓰인다.

## 7. 최적화 (제안, 팀과 결정)

### 7.1 순서

**① 링크드 클론 검증 → ② 그래도 느리면 최소 사양 워밍 풀 → ③ 풀이 비면 지금 방식으로 자동 폴백**

### 7.2 워밍 풀

- 원하는 사양을 예측할 수 없다. 최대 사양으로 만들어 두고 낮추면 시간이 걸리고, SSD는 줄일 수 없어서 원한 것보다 큰 SSD가 할당된다
- 그래서 **최소 사양으로 만들어 두고, 넘길 때 늘린다**

| 미리 해 두는 것 (오래 걸림) | 넘겨줄 때 하는 것 (빠름) |
|---|---|
| 클론 (템플릿 기본 크기, 정지 상태) | CPU·RAM 설정 — 꺼진 VM이라 즉시 |
| | 디스크를 고른 크기로 확장 — 게스트 파티션은 첫 부팅 때 cloud-init이 늘림 |
| | cloud-init(계정·비밀번호·IP) 주입 후 시작 |

- 조건: 최소 디스크 사양 = 템플릿 기본 디스크 크기 / 풀 VM은 한 번도 부팅하지 않은 상태로 둔다 / 템플릿이 바뀌면 풀을 비우고 다시 채운다 / 풀이 비면 기존 방식으로 폴백한다(필수 경로가 아니라 최적화) / 풀 VM은 플랫폼(운영) 몫으로 센다. 가장 많이 쓰는 OS에만 둔다
- **링크드 클론이 되면 가치가 크게 줄어든다.** 그때 남는 병목은 부팅 시간인데, 이를 숨기려면 풀 VM을 켜 둬야 하고 그러면 RAM을 먹는다. RAM이 병목인 환경에서는 손해다

### 7.3 기다리는 동안 할 일

| 단계 | 클론 중에 미리 할 수 있나 |
|---|---|
| 내부 주소 할당 | 이미 클론 앞에 있음 |
| 포트 번호 계산·예약 | 가능 — 주소와 VM 번호가 이미 정해져 있다 |
| 포트 규칙 등록 | 가능 — VM이 없어도 규칙은 들어간다. 부팅 전엔 갈 트래픽이 없을 뿐 |
| HTTPS 라우트 등록 | 가능 |
| cloud-init 사용자데이터 생성 | 가능 |
| DB 기록·알림 준비 | 가능 |
| config 설정·디스크 확장·시작 | 불가 — 클론이 끝나야 한다 |

- 한 명만 만들 때는 10~20초 정도 줄어든다. 진짜 이득은 여러 명이 몰릴 때의 **파이프라인**이다. 클론은 한 번에 하나뿐이니, A가 클론하는 동안 B·C의 준비를 끝내 두면 A가 끝나는 즉시 B의 클론이 시작된다
- 미리 넣은 규칙은 생성이 실패하면 반드시 회수한다. 선언형 조정(6.3)이면 자동으로 처리된다

### 7.4 상태 캐시

- 고정 주기 폴링은 과하다. 실제 필요량(VM 생성 요청 + 대시보드 조회)보다 훨씬 많이 묻게 되고, Proxmox가 약 10초마다 갱신하므로 5초마다 물어도 같은 값을 두 번 받는다
- **제안: TTL 10초, 요청이 있을 때만 갱신.** 캐시가 10초 이내면 그대로 주고, 오래됐으면 그때 한 번 조회한다. 아무도 안 물으면 호출 0회, 20명이 동시에 봐도 10초에 노드당 1회다. VM 생성 직전처럼 정확도가 중요한 순간에는 강제로 조회한다

### 7.5 진행 상황 표시

- Go → Kotlin에 단계 보고 → Kotlin이 브라우저에 스트리밍(SSE). Go는 내부 전용이라 브라우저가 직접 붙지 않는다
- 표시는 퍼센트보다 **단계**다: `대기 중(앞에 N명) → 복제 중 → 설정 중 → 부팅 중 → 네트워크 등록 중 → 완료`. Proxmox 작업 상태가 진행률을 항상 주지는 않는다
- 클론이 직렬이라 대기 줄이 실제로 생긴다. "앞에 몇 명"을 보여 주면 막연한 스피너보다 체감이 낫다
- 실패하면 어느 단계에서 왜 실패했는지 보여 준다

## 8. 열린 질문 (팀과 정할 것)

- 모델 2 + 설정성 자원에 모델 3 혼합으로 확정할지
- 계약 형식: REST + OpenAPI / gRPC
- 링크드 클론 검증, 워밍 풀 도입 여부와 크기
- 진행률 표시에 대기 순번을 넣을지
- Kotlin 프레임워크 — Spring Boot를 쓰면 22번의 애너테이션 + AOP 방식과 자연스럽게 맞는다
- 스케줄러 중복 실행 방지 ([22번](../rules/authorization.md)의 분산 락)
- Kotlin ↔ Go 계약에서 쓰는 식별자 — 23번에 따라 unique resource id로 하는 것이 방향이다
