# 25번(원터치 배포) — 앱 배포 서비스 기획 요약

> 이 문서는 **확정한 기획의 요약**이다. 구현 세부(API 구조, 상태 이름, 빌드·실행 환경의 구성)는 담당이 개발하면서 정한다.
>
> 함께 읽을 문서: [21번(팀과 역할)](../rules/team-ownership.md) · [22번(권한 판단)](../rules/authorization.md) · [23번(자원 이름 규칙)](../rules/resource-naming.md) · [서버리스](serverless.md) · [데이터베이스](database.md)

## 1. 무엇을 하는 서비스인가

GitHub 저장소를 연결하면 GSMSV가 코드를 빌드해서 띄우고, 공개 주소와 HTTPS까지 붙여 준다. 학생이 서버를 직접 관리하지 않고 웹 앱을 배포한다.

- **기준 모델은 Railway다.** "저장소 연결 → 자동 빌드 → `PORT`로 실행 → 공개 주소 → push하면 자동 재배포" 흐름을 그대로 가져오고, 이미 정한 GSMSV 규칙(격리, 소유·권한, 한도, DB)과 부딪히는 곳만 바꾼다
- **맡는 범위**: 계속 떠 있는 프로그램이다. 웹 서버 앱, 정적 사이트, 워커(공개 주소 없이 계속 도는 프로세스), 크론(정해진 시각에 돌고 끝나는 작업). 60초 안에 끝나는 짧은 함수는 [서버리스](serverless.md)가 맡는다. root 권한이나 Docker 직접 사용, 리눅스 학습이 필요한 것은 VM에 남는다

용어

| 용어 | 뜻 |
|---|---|
| 앱 | 이 서비스의 서비스 자원(`app-…`). Railway의 "프로젝트"에 해당한다. 서비스와 환경을 묶는다 |
| 서비스 | 앱 안의 실행 단위 하나(예: frontend, backend, worker). 앱의 하위 자원이다. 23번의 "서비스 자원"과 다른 말이다 |
| 환경 | 앱 안의 서비스 세트 하나(예: production, staging, PR 환경). 앱의 하위 자원이다 |
| 칸 | "서비스 × 환경" 하나. 실제로 도는 컨테이너 하나에 해당한다. 하위 자원이 아니라 그 칸의 설정값과 부품으로 다룬다 |
| 배포 기록 | 빌드·배포 한 번. 되돌리기의 대상이다. 앱의 하위 자원이다 |

## 2. 누가 무엇을 할 수 있는가

| 동작 | 개인 앱 | 팀 앱 |
|---|---|---|
| 앱·서비스·환경·배포 상태·로그·사용량 그래프·설정(일반 변수) 보기 | 본인 | 팀원 전원 |
| 사용 기간 연장 신청 | 본인 | 팀원 전원 |
| 앱·서비스·환경 만들기·지우기 | 본인 | 팀장·DevOps |
| 저장소 연결, 설정·변수 바꾸기, 상시 실행 켜기 | 본인 | 팀장·DevOps |
| 콘솔에서 배포·재시작·되돌리기 | 본인 | 팀장·DevOps |
| 배포 승인·거절 | 본인 | 팀장·DevOps |
| 도메인 연결, PR 미리보기 설정 | 본인 | 팀장·DevOps |
| 콘솔 셸 접속 | 본인 | 팀장·DevOps |

- [서버리스](serverless.md)와 같은 틀이다. 설정값으로 분류한 것은 팀장·DevOps만 바꾼다
- 개인 앱 ↔ 팀 앱 전환은 하지 않는다
- 관리자는 "관리자는 모든 동작 허용" 규칙으로 모든 동작을 할 수 있다
- 시스템(자동): push·PR을 받아 배포 시작·승인 대기, 빌드, 잠자기·깨우기, 재시작, 크론 실행, 로그·배포 기록 정리, PR 환경 정리, 만료 처리, 졸업 정리, 알림
- **GitHub에 push할 수 있는 사람과 GSMSV 역할이 다르다.** 일반 팀원도 저장소 쓰기 권한이 있으면 연결한 브랜치에 push하고 PR을 열 수 있다. 그래서 **배포 승인 단계**를 둔다 (4장). 저장소 쓰기 권한 자체는 GitHub가 정하는 일이라 GSMSV가 막지 않는다

## 3. 자원 구조

```text
grn:{소유자 id}:app-…                 ← 23번 서비스 자원 (소유자: 개인 또는 팀)
 ├ /service-…     서비스 (소스·빌드·시작 명령·공개 주소 유무·종류)
 ├ /env-…         환경 (production 기본, staging 등 추가, PR 환경)
 ├ /domain-…      도메인 연결 (어느 칸에 붙는지는 설정값)
 └ /deployment-…  배포 기록 (어느 칸의 배포인지는 설정값)
칸(서비스 × 환경) = 실제로 도는 컨테이너. 칸의 설정은 설정값, 컨테이너·라우트는 부품
```

- id는 `app-` 뒤에 무작위 12자다. 접두사를 `project`로 하지 않은 이유: 프로젝트 오너를 없앴고(21번), v2에는 프로젝트 개념이 없으므로 프로젝트 소유가 돌아온 것으로 오해할 수 있다. `deploy`로 하지 않은 이유: "배포 한 번"(배포 기록)과 헷갈린다
- 하위 자원은 한 단계만 둔다([23번](../rules/resource-naming.md)). 그래서 칸은 하위 자원으로 만들지 않고, 칸을 다루는 요청은 서비스 id와 환경 id를 함께 받는다. 자원 로더는 두 id가 모두 요청에 적힌 앱의 것인지 확인한다
- 설정값
  - 앱: 이름, 사용 기간, PR 미리보기 켜기와 기준 환경
  - 서비스: 종류(웹·워커·크론), 소스(GitHub 저장소와 폴더 / 컨테이너 이미지 / 압축 파일), 시작 명령, 공개 주소 여부, 상태 확인 경로, 배포 전 명령과 시간 상한, 크론이면 cron 식
  - 환경: 연결한 브랜치, 자동 재배포, CI 기다리기
  - 칸: 메모리·CPU, 환경변수(변수마다 비밀 표시), 연결한 DB, 상시 실행 여부, 서브도메인(production)

## 4. 코드 받기, 빌드, 실행, 배포

### 코드 받기

- 서비스마다 GitHub 저장소(모노레포 폴더·감시 경로 지정 가능) / 컨테이너 이미지 / 압축 파일(최대 100 MiB) 중 하나를 쓴다
- GitHub 말고 다른 Git은 받지 않는다

### 빌드

- 자동 감지 빌더가 기본이고, `Dockerfile`이 있으면 `Dockerfile`을 쓴다
- **빌드도 학생 코드 실행으로 보고** 학생 코드를 돌리는 노드 묶음에서 격리한다. 빌드 중 바깥 통신은 웹 포트만 열고, 비밀 변수는 빌드에 넘기지 않는다
- 1회 25분, 소유자당 동시 1개, 빌드 캐시는 앱마다 따로 둔다

### 실행

- [서버리스](serverless.md)와 같은 종류의 샌드박스 컨테이너에서 실행한다
- 웹 서비스는 들어오는 요청이 **10분 없으면 재우고**, 요청이 오면 깨운다. 재우지 않으려면 상시 실행 한도 안에서 켠다. 워커는 항상 실행한다
- 복제는 1개다. 새 배포는 상태 확인이 2xx를 돌려줄 때까지 옛 배포를 유지한다 (300초). 오류로 멈추면 재시작은 최대 10회다
- 볼륨은 1차에 없다. 임시 디스크에는 상한을 둔다

### 배포 승인과 흐름

- push한 GitHub 사용자가 GSMSV에서 그 앱을 배포할 권한(개인 앱은 소유자, 팀 앱은 팀장·DevOps)이 있으면 바로 진행하고, 없으면 팀장·DevOps(개인 앱은 소유자)가 승인한 뒤 빌드한다. PR 미리보기도 같다
- 흐름: CI 통과 → 승인 → 빌드 → 배포 전 명령 → 배포
- 승인 대기 중에 새 push가 오면 교체하고, 7일이 지나면 자동 취소한다. 콘솔에서 직접 한 배포·되돌리기는 승인이 필요 없다
- **배포 기록**은 칸마다 10개를 둔다. 되돌리기는 이미지만 되돌리고 변수는 지금 값을 쓴다

### 환경과 PR 미리보기

- 앱당 환경은 3개까지 나눌 수 있다
- PR 미리보기: GSMSV에 GitHub를 연결한 소유자의 PR만 만든다. 봇 PR은 기본으로 끈다. 기준 환경의 변수와 DB를 복사한다. PR이 닫히거나 7일 쉬면 삭제한다
- 내부 주소는 같은 앱, 같은 환경 안에서만 닿는다

## 5. 주소와 네트워크

- 공개 주소는 [서버리스](serverless.md)와 같은 **별도 도메인**을 쓰고, 함수 주소와 이름 공간을 나눈다. production의 서브도메인은 학생이 고르고, 나머지는 자동으로 붙인다
- 사용자 지정 도메인은 칸마다 2개이고, DNS TXT 레코드로 소유를 확인한다
- **네트워크**: 바깥으로 나가는 통신은 웹 포트만 열고, 학생 VM·사설 대역·다른 앱의 내부 주소로는 나가지 못하게 막는다. 메일 발송이나 포트 스캔 같은 남용을 막기 위한 것이다. 받아들인 단점: 외부 DB 서비스(다른 포트)는 쓸 수 없다. 대신 GSMSV의 [데이터베이스](database.md)를 안내한다
- 칸마다 자기 DB([데이터베이스](database.md))를 고를 수 있다. DB 비밀번호를 교체하면 그 칸을 자동으로 재시작한다

## 6. 환경변수, 설정 파일, 크론, 셸

- **환경변수**: [서버리스](serverless.md)와 같은 비밀 변수 규칙을 쓴다. 칸마다 32 KB까지이고, 저장하면 자동으로 재시작한다
- **GSMSV 설정 파일**: 저장소에 설정 파일이 있으면 **그 배포에 한해** 파일 값이 콘솔 값보다 우선한다
- **크론**: 서버리스 예약 규칙(서울 시간대, 5칸, 최소 5분, 앞 실행이 끝나지 않으면 건너뜀)에 최대 실행 시간 30분을 더한다
- **배포 전 명령**: 기본 10분, 최대 30분이다. 실패하면 배포를 중단한다
- **콘솔 셸**: 팀장·DevOps(개인 앱은 소유자)만 쓰고, 감사 로그에 남기며 최대 1시간까지 연결한다

## 7. 로그와 사용량

- 실행 로그는 칸마다 **3일 또는 50 MiB**를 둔다. 빌드 로그는 배포 기록과 함께 둔다
- HTTP 접근 기록은 만들지 않는다. 메모리·CPU 사용량 그래프는 만든다

## 8. 사용량 한도 (모두 설정값)

| 항목 | 값 |
|---|---|
| 메모리 할당량 합계 | 개인 2 GiB, 팀 4 GiB (잠든 칸·PR 환경 포함) |
| 칸마다 | 메모리 기본 512 MiB·최대 1 GiB, CPU 최대 1 vCPU |
| 앱 개수 | 개인 2개, 팀 4개 |
| 앱당 | 서비스 5개, 환경 3개, 동시 PR 환경 2개 |
| 상시 실행 칸 | 개인 1개, 팀 2개 |

## 9. 수명

- 앱 단위로 VM과 같은 주기로 만료된다 ([기능별 정책](../policies/feature-policies.md))
- 정지는 모든 서비스·환경을 멈추고, 요청이 와도 깨어나지 않는다
- **앱이나 함수를 연장하면, 연결한 DB도 더 늦은 쪽 만료일에 맞춰 함께 연장한다**
- 졸업·팀 해체·삭제 확인은 [데이터베이스](database.md)·[서버리스](serverless.md)와 같다

## 10. 1차에서 하지 않는 것

- 템플릿
- 다른 Git 서비스
- 볼륨
- 복제 2개 이상
- 공유·참조 변수
- HTTP 접근 기록

## 11. 정하지 않은 것

| 항목 | 정하는 사람 |
|---|---|
| API 구조, 상태 이름, 앱·서비스·환경의 이름 규칙 | 백엔드 담당 |
| 빌드·실행 환경의 구성(네임스페이스 단위, 공개 주소 라우팅 부품) | 인프라 담당 |
